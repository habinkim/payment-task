# 수평 확장 시 동시성 검토

작성: 2026-08-12 · 대상 커밋: `f3f6925` (PR #13 기준) · 상태: 검토 완료, **1순위 수정 완료([ADR 0012](adr/0012-conditional-update-for-state-transition.md))**

## 문제 제기

성능 한계에 부딪혀 WAS와 DB를 수평 확장한다고 가정할 때, 지금 코드가 무엇을 지키고 무엇을 놓치는지 확인했다.

출발점은 이 질문이다. **지금 정합성을 지키는 것이 무엇인가.** 코드를 읽어보면 셋뿐이다.

| 보장 | 수단 |
|---|---|
| 멱등성 | `uk_merchant_payment_no` UNIQUE |
| 원자적 차감 | `UPDATE ... WHERE balance >= :amount` |
| 상태 일관성 | 단일 트랜잭션 |

JVM 락(`synchronized`, `ReentrantLock`)은 **프로덕션 코드에 0건**이다. 이건 좋은 신호다 — JVM 락은 수평 확장 시 조용히 무력화되어 "단일 서버에선 되는데 늘리면 깨지는" 최악의 버그를 만드는데, 이 코드는 그 함정에 애초에 빠지지 않았다. 다만 **분산 락으로 대체된 것도 아니라서, 위 셋이 무너지면 보호가 없다.**

## 현상 — 실측한 것

### 이중 차감이 재현된다

두 인스턴스가 같은 `UNKNOWN` 건을 동시에 확정하는 상황을 재현했다.

```
A가 본 상태 = UNKNOWN, B가 본 상태 = UNKNOWN
confirm 성공: COMPLETED      ← 둘 다 성공
confirm 성공: COMPLETED
지갑 잔액 10.0000 → 4.0000
실제 차감 = 6.0000 (정상 3.0000)
```

**예외 0건, orphan 카운터 0건.** 두 스레드 모두 정상 종료했다.

### 위험도가 잔액에 반비례한다

| 잔액 대비 결제액 | 결과 |
|---|---|
| 60% (빠듯함) | 차감 1회 — `balance >= amount`가 두 번째를 막음 |
| **30% (넉넉함)** | **차감 2회, 예외 없음, 로그 없음** |

잔액이 충분할수록 조건이 통과해 아무도 막지 못한다. `ck_wallet_balance_non_negative` CHECK도 발동하지 않는다. **감지 수단이 없는 손실**이다.

### 스케줄러는 100% 겹친다

```
A가 집은 건수 = 3, B가 집은 건수 = 3, 겹침 = 3
```

`findOldestUnknown()`은 `created_at ASC` 정렬의 평범한 SELECT다. `FOR UPDATE`도, claim 컬럼도, 상태 선점도 없다. 정렬이 결정적이라 **모든 인스턴스가 동일한 목록**을 가져간다.

`application-prod.yaml`이 `payment.reconcile.enabled: true`를 박아두므로, prod로 N대를 띄우면 N개 스케줄러가 60초마다 같은 50건을 각자 처리한다.

### 결제 경로는 안전하다

```
pay 실패: ApiException      ← 한쪽만 실패
성공 건수 = 1, 차감 = 3.0000 (정상)
```

`openPending()`이 `DataIntegrityViolationException`을 잡아 `DUPLICATE_PAYMENT_NO`(409)로 변환한다. **UNIQUE 제약이 직렬화 지점**이라 차감까지 가지 못한다.

## 원인 — 설계의 비대칭

결제와 확정의 차이는 **INSERT냐 UPDATE냐**다.

```java
// 결제: INSERT → UNIQUE가 막는다
ledgerStore.append(new Payment(...));          // uk_merchant_payment_no

// 확정: UPDATE → 아무도 막지 않는다
if (walletStore.deductIfEnough(...)) {          // ① 차감 먼저, 조건은 balance뿐
    payment.complete(...);                      // ② 방어는 메모리 status뿐
}
ledgerStore.updateState(payment);               // ③ WHERE id=? 무조건 덮어쓰기
```

두 겹의 구멍이 있다.

**하나. `transitionTo()`가 메모리 사본을 본다.**

```java
private void transitionTo(PaymentStatus next) {
    if (status.isTerminal()) { throw ...; }     // this.status = 인스턴스 필드
```

`Payment`는 JPA 엔티티가 아닌 POJO다. 영속성 컨텍스트에 붙어 있지 않아 락도 버전도 없다. A가 커밋해 DB가 `COMPLETED`가 돼도 B의 객체는 `UNKNOWN` 스냅샷 그대로라 통과한다.

**둘. `updateState()`가 조건 없는 덮어쓰기다.**

```sql
UPDATE payment SET status=?, ... WHERE id=?     -- 기대 상태 조건 없음, @Version 없음
```

Last-write-wins다. 예외도 로그도 affected-rows 검사도 없다. `deductIfEnough`는 조건부 UPDATE로 제대로 짜여 있는데 **정작 상태 전이만 무방비**라는 비대칭이 근본 원인이다.

더 깊게 보면 **차감에만 원장이 없다.**

| | 원장 테이블 | 멱등 보장 |
|---|---|---|
| 결제 생성 | `payment` + UNIQUE | ○ |
| 충전 | `wallet_charge` + UNIQUE | ○ |
| **차감** | **없음** (`wallet.balance` 갱신뿐) | ✕ |

충전에는 원장을 뒀는데 차감에는 없다. DB가 "결제 1건당 차감 1회"를 구조적으로 강제할 방법이 없는 이유다.

## DB를 늘리면 — 전제가 무너진다

위 분석은 **DB 1대**를 가정했다. UNIQUE가 직렬화해준다는 것도 단일 DB일 때 얘기다.

**읽기 복제(Read Replica).** `findOldestUnknown()`이 `@Transactional(readOnly = true)`다. Replica로 라우팅되면 복제 지연 때문에 **이미 확정된 건을 UNKNOWN으로 착각**해 이중 차감 확률이 올라간다. `readOnly` 트랜잭션은 코드에 7곳 있다.

**샤딩.** `uk_merchant_payment_no`가 **샤드별 인덱스**가 된다. 같은 결제번호가 다른 샤드에 들어가면 멱등이 깨진다 — 지금 멱등 설계 전체가 이 제약 하나에 걸려 있다. `wallet_id`로 샤딩하면 결제의 `payment` INSERT와 `wallet` UPDATE가 크로스 샤드가 되어 분산 트랜잭션(2PC/Saga)이 필요해진다.

이 두 항목은 H2 인메모리라 **재현하지 못했다.** 구조 분석에 의한 판정이며, 실측한 이중 차감과는 근거 등급이 다르다.

### 선결 과제 — prod도 H2 인메모리다

`datasource` 정의가 `application.yaml` 한 곳뿐이고 `application-prod.yaml`에 오버라이드가 없다. 인메모리 DB는 JVM 프로세스에 종속되므로, **지금 3대를 띄우면 DB가 3개**다. 잔액도 원장도 인스턴스마다 갈라진다.

과제 명세가 H2/SQLite를 요구했으므로 이 자체는 결함이 아니다. 다만 **수평 확장 논의가 성립하려면 공유 DB가 선결 조건**이다.

## 시도한 실험

프로덕션 코드는 건드리지 않고 프로브 테스트로만 확인한 뒤 제거했다.

| 실험 | 방법 | 결과 |
|---|---|---|
| 확정 이중 차감 | 같은 `UNKNOWN` 건의 `Payment` 사본 2개로 동시 `confirm()` | **재현** — 3원 결제에 6원 차감 |
| 잔액별 위험도 | 결제액을 잔액의 60% / 30%로 변경 | 60%는 1회, **30%는 2회** |
| 스케줄러 겹침 | `findOldestUnknown(10)` 두 번 호출 후 교집합 | **3/3 전부 겹침** |
| 결제 경로 | 같은 `merchantPaymentNo`로 동시 `pay()` | 안전 — 1건만 성공 |

## 외부 리서치

### 스케줄러 중복 — ShedLock은 효율성 락이다

Spring `@Scheduled`는 인스턴스 수만큼 그대로 실행된다. 프레임워크 차원의 조정 장치가 없다.

ShedLock은 잡 실행 직전 공유 저장소에 락 레코드를 쓰고 성공한 인스턴스만 실행한다. 기존 `@Scheduled`를 그대로 두므로 도입 비용이 가장 낮다. `lockAtMostFor`를 **실제 작업 시간보다 길게** 잡는 것이 핵심이다 — 짧으면 느린 잡이 중복 실행된다. `usingDbTime()`으로 노드 간 클럭 스큐를 우회한다.

Quartz clustering은 NTP 1초 이내 동기화가 필수이고 노드 3개를 넘으면 락 경합으로 성능이 떨어진다.

출처: [The New Stack](https://thenewstack.io/rethinking-java-scheduled-tasks-in-kubernetes/) · [Redisson 블로그](https://redisson.pro/blog/distributed-task-scheduling-in-java-quartz-shedlock-redisson.html)

### 멱등성 — UNIQUE만으로는 부족하다

[Brandur의 idempotency keys](https://brandur.org/idempotency-keys)가 이 주제의 정본이다.

> UNIQUE는 동시 요청 중 하나만 통과시키는 하드 백스톱은 맞다. 그러나 **행의 존재 여부만** 알려줄 뿐 **진행 상태를 모른다.**

재시도는 대개 첫 요청이 끝나기 전에 도착한다 — 끝났으면 응답을 받았을 테니 재시도할 이유가 없다. 그래서 `IN_PROGRESS`/`COMPLETED` 상태기계와 `recovery_point`가 필요하다는 것이 Brandur의 논지다.

이 프로젝트는 `PaymentStatus`로 이미 상태기계를 갖췄고, `resolveDuplicate()`가 non-terminal에 409를 던지는 것도 in-flight 시맨틱과 일치한다. **방향이 맞다.**

다만 갭이 하나 있다. **같은 `merchantPaymentNo`에 다른 `amount`가 오면 기존 건을 그대로 반환한다.** Stripe는 `idempotency_error`를, Toss Payments는 파라미터 불일치 에러를 낸다. 요청 파라미터 해시 비교가 없다.

출처: [Stripe API](https://docs.stripe.com/api/idempotent_requests) · [Toss Payments 멱등키](https://docs.tosspayments.com/reference/using-api/idempotency-key)

### read-then-act — MySQL RR이 더 안전하다는 착각

반직관적인 사실 하나를 확인했다.

| | MySQL InnoDB RR | PostgreSQL RR |
|---|---|---|
| Lost Update (SELECT→UPDATE) | **막지 못함** | first-updater-wins로 abort |
| Phantom (locking read) | next-key lock으로 방지 | — |

InnoDB RR에서 **plain SELECT는 non-locking snapshot read**라 락을 걸지 않는다. 격리 수준 기본값이 PostgreSQL보다 높다고 해서 lost update를 막아주지 않는다.

이것이 이 프로젝트에 직결된다. **H2는 READ COMMITTED, MySQL InnoDB는 REPEATABLE READ**인데 동시성 테스트가 전부 H2 위에서 돈다. 내가 재현한 이중 차감은 MySQL에서 **더 잘 재현된다** — RR 스냅샷 때문에 B가 A의 커밋을 볼 수 없기 때문이다.

출처: [Percona](https://www.percona.com/blog/what-if-mysqls-repeatable-reads-cause-you-to-lose-money/) · [Jepsen: MySQL 8.0.34](https://jepsen.io/analyses/mysql-8.0.34)

### 분산 락 — 정확성에는 쓰지 말라

[Kleppmann의 분석](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)이 핵심 구분을 준다.

**효율성 락**은 실패해도 중복 작업 정도지만, **정확성 락**은 실패하면 데이터 손실이다. 락은 사실 lease이고, GC pause·페이지 폴트·네트워크 지연으로 클라이언트가 만료를 알아채지 못하면 안전하지 않은 쓰기를 한다. GitHub은 약 90초 패킷 지연을 겪은 적이 있다.

> You simply cannot make any assumptions about timing.

제대로 하려면 **fencing token**이 필요하고, 이는 **리소스 쪽이 토큰을 검사해 거부**해야 성립한다. Redlock에는 이 기능이 없다.

Kleppmann의 결론이 이 프로젝트의 방향을 정해준다.

> 정확성이면 합의 시스템이나 **최소한 제대로 된 트랜잭션 보장을 가진 DB**를 쓰라.

즉 이중 차감은 **락이 아니라 DB 제약으로 풀어야 한다.**

### 외부 호출과 트랜잭션 경계

TCC(Try-Confirm-Cancel)의 결제 도메인 실체는 **승인/매입 분리**다. Try에서 PG authorize, Confirm에서 capture. 내부 트랜잭션 커밋 **후에** capture를 호출하면 orphan 창이 줄어든다.

Saga의 함정은 **격리성 부재**다. 보상하려는 사이에 잔액이 빠져나가면 보상 자체가 불가능해진다. 그래서 **차감을 먼저, 지급을 나중에** 하는 순서 설계가 필요하다.

이 프로젝트는 [ADR 0001](adr/0001-external-call-outside-transaction.md)에서 이미 TX1(PENDING 커밋) → 외부 호출 → TX2(차감+확정)로 쪼갰고, [ADR 0004](adr/0004-timeout-is-indoubt.md)에서 조회 기반 정합성 확인을 뒀다. 리서치가 권하는 구조와 일치한다.

## 개선 방향

레버리지(효과÷비용) 순으로 정렬했다.

### 0순위 — 공유 DB (선결)

수평 확장을 논하려면 인스턴스가 같은 DB를 봐야 한다. 과제 범위에서는 H2가 맞으므로, **README에 "단일 인스턴스 전제"를 명시**하는 것으로 갈음한다.

### 1순위 — `updateState()`를 CAS로 ☑ 완료

```sql
UPDATE payment SET status=?, ...
 WHERE merchant_payment_no=? AND status=:expectedStatus
```

affected rows가 0이면 다른 인스턴스가 이미 처리한 것이므로 예외를 던져 롤백한다. **차감도 함께 되돌아간다.**

이 방식을 택하는 이유가 셋이다.

- **락도 미들웨어도 필요 없다.** Kleppmann이 말한 "제대로 된 트랜잭션 보장을 가진 DB"를 쓰는 것이다.
- **결제(INSERT+UNIQUE)와 원리가 같다.** DB가 직렬화 지점이 된다.
- **경로와 무관하게 막는다.** 스케줄러든 관리자 API든 상관없다.

`deductIfEnough`가 이미 조건부 UPDATE인데 `updateState`만 무조건 덮어쓰기라는 비대칭을 메우는 것이기도 하다.

부수 효과로 현재 `updateState`의 불필요한 SELECT 왕복이 사라진다.

**적용 결과([ADR 0012](adr/0012-conditional-update-for-state-transition.md))**

| | 수정 전 | 수정 후 |
|---|---|---|
| 동시 확정 2건 | 둘 다 성공, **6원 차감**(정상 3원) | 1건 성공, **3원 차감** |
| 잔액 넉넉할 때 | **이중 차감, 감지 불가** | 차감 1회 |
| 이미 확정된 건 재확정 | 조용히 덮어씀 | `PAYMENT_ALREADY_SETTLED` |
| 테스트 | 218건 통과(결함 미검출) | 222건 통과 |

CAS 조건을 제거하자 신규 4건이 **전부 실패**해 조건이 실제 방어선임을 확인했다.

### 2순위 — `WalletChargeService`의 예외 처리 위치

`append()`가 `DataIntegrityViolationException`을 **같은 트랜잭션 안에서** 잡는다. 트랜잭션은 이미 rollback-only로 마킹되어 있어 커밋 시점에 `UnexpectedRollbackException`이 난다. MySQL REPEATABLE READ에서는 재조회도 첫 스냅샷을 보므로 **100% 실패**한다.

금전 정합성은 UNIQUE가 지키므로 이중 충전은 없다. 다만 **멱등 재요청이 200 대신 500**으로 끝난다. `REQUIRES_NEW`로 분리하거나 트랜잭션 밖에서 잡아야 한다.

H2에서는 재현되지 않아 현재 테스트가 통과한다. 이것이 2순위인 이유이자, 아래 4순위가 필요한 이유다.

### 3순위 — 스케줄러 단일화

ShedLock을 도입해 배치가 한 인스턴스에서만 돌게 한다.

**정확성이 아니라 효율성 목적**이다. 1순위를 적용하면 중복 실행이 일어나도 정합성은 지켜지고, ShedLock은 게이트웨이 호출 낭비를 줄인다. Kleppmann의 구분에 따르면 fencing token까지 갈 필요가 없는 영역이다.

### 4순위 — 동시성 테스트를 MySQL에서

H2(READ COMMITTED)와 MySQL(REPEATABLE READ)의 격리 수준이 다르다. Testcontainers로 동시성 IT만 MySQL에서 돌리면 2순위 같은 문제를 잡을 수 있다.

Flyway + 표준 SQL이라 전환 비용이 낮다.

### 5순위 — 멱등 키 파라미터 검증

같은 `merchantPaymentNo`에 다른 `amount`가 오면 거부한다. Stripe·Toss의 표준 동작이다.

## 한계

- **DB 다중화(복제·샤딩) 시나리오는 재현하지 못했다.** H2 인메모리 제약이다. 구조 분석에 의한 판정이며 실측과 근거 등급이 다르다.
- **부하 수준을 측정하지 않았다.** "성능 한계에 부딪혔을 때"를 가정했을 뿐, 실제로 언제 한계가 오는지는 모른다. 스케일아웃 시점 판단은 별도 측정이 필요하다.
- **2~5순위는 아직 제안이다.** 1순위만 적용했고 나머지는 검증되지 않았다.
