# PRD-002. 조회와 정합성 확인

| 항목 | 값 |
|---|---|
| 상태 | **예정** |
| 선행 | [PRD-001](PRD-001-결제플로우.md) |
| 대응 스펙 | [SPEC](../SPEC.md) §5.2~5.5, §7 관측성, §8.2 시나리오 검증 |

---

## 무엇을 왜 만드나

PRD-001이 결제를 처리했다면, 이 사이클은 **처리된 결과를 쓸 수 있게** 만든다.

명세 1번의 두 번째 요구가 이것이다.

> "가상의 고객에 대해 컴플레인을 고려하여 운영상의 모니터링이 가능한 정보를 제공하여야 합니다."

실패 이력을 저장하는 것만으로는 이 요구가 충족되지 않는다. **CS 담당자가 그 기록만 보고 고객에게 답변할 수 있어야** 한다. 조회 수단이 없으면 저장은 무의미하다.

## 이 사이클이 풀어야 하는 문제

**결과를 모르는 결제가 남아 있다.** PRD-001에서 타임아웃 건을 `UNKNOWN`으로 기록했지만 확정하는 수단이 없다. 이 상태로 두면 고객 돈이 어디 있는지 아무도 모른다.

그리고 **HTTP 계층 설정이 한 번도 검증되지 않았다.** PRD-001은 인프로세스 Mock만 썼으므로, connect와 read 타임아웃이 실제로 동작하는지 확인된 적이 없다([ADR 0007](../adr/0007-mock-gateway-in-production.md)). 설정값이 파일에 적혀 있다는 것은 대리지표다.

## 범위

**포함**

- `GET /api/v1/payments/{paymentNo}` — 단건 조회
- `GET /api/v1/wallets/{walletId}` — 지갑 조회
- `GET /api/v1/payments` — 목록 조회(상태·지갑·기간 필터, 페이징)
- `POST /api/v1/admin/payments/{paymentNo}/reconcile` — 정합성 확인
- 정합성 확인 스케줄러
- 게이트웨이 장애 주입 — 확률 기반 실패를 켜고 끄는 설정
- 메트릭 카운터

**제외**

| 항목 | 이유 |
|---|---|
| 지갑 충전 | PRD-003 |
| 자동 대사 배치 | `UNKNOWN` 건이 수동 처리 한계를 넘을 때 도입([SPEC](../SPEC.md) §10 확장) |
| 보상 취소 호출 | 취소 API 명세가 과제에 없다 |
| `HttpPaymentGatewayClient` | 연동할 실제 게이트웨이가 없다. 아래 참조 |
| WireMock 통합 테스트 | 검증할 HTTP 계층이 존재하지 않는다 |
| `payment.gateway.base-url`, `connect-timeout`, `read-timeout` | 향할 대상이 없는 설정이다. 제거한다 |

## 왜 조회를 `paymentNo`로 하나

서버 PK가 아니라 `paymentNo`로 조회한다. 타임아웃으로 응답을 받지 못한 3rd party도 조회할 수 있어야 하기 때문이다. 서버가 발급한 ID로 조회하게 만들면, **조회가 가장 절실한 상황에서 조회할 수 없다.**

이것이 [ADR 0002](../adr/0002-payment-no-as-idempotency-key.md)에서 결제번호를 클라이언트가 생성하도록 정한 이유이며, 이 사이클에서 그 판단의 실익이 드러난다.

## HTTP 클라이언트 대신 장애 주입을 만든다

초안은 `HttpPaymentGatewayClient`를 만들고 WireMock으로 타임아웃과 연결 실패를 검증하려 했다. 철회한다.

**연동할 실제 게이트웨이가 없다.** 과제가 요구한 것은 가상의 3rd party이고, HTTP 클라이언트를 만들어도 향할 곳은 WireMock뿐이다. 그러면 `read-timeout: 3s`는 *존재하지 않는 외부를 향한 설정*이 되고, 그것을 검증하려고 WireMock을 띄우는 것은 검증을 위한 검증이다. 설정을 지우면 검증할 것도 사라진다.

**정작 필요한 것은 따로 있다.** 지금 모의 게이트웨이는 `paymentNo` 접두어로만 실패한다. 평가자가 `TIMEOUT-`을 붙여야 타임아웃을 본다는 뜻이며, **정상 결제를 반복하다 우연히 실패를 만나는 상황**은 재현되지 않는다. 그런데 재시도와 정합성 확인이 필요한 진짜 이유가 바로 그 상황이다.

확률 기반 장애 주입을 둔다.

```yaml
payment:
  gateway:
    mode: mock
    chaos:
      enabled: false
      timeout-rate: 0.0
      failure-rate: 0.0
```

기본값은 전부 꺼짐이다. 켜지 않으면 기존 동작이 그대로다. 접두어 지정은 확률보다 우선하므로, `TIMEOUT-`을 붙인 요청은 카오스가 켜져 있든 아니든 항상 타임아웃이 된다. 의도한 시나리오가 확률에 흔들리면 테스트가 깨진다.

이렇게 하면 스케줄러가 실제로 쌓인 `UNKNOWN`을 처리하는 모습을 볼 수 있다. 접두어로 하나씩 만들어 넣는 것과는 다르다.

**난수는 주입한다.** `Random`을 생성자로 받아 테스트에서 시드를 고정한다. 확률 로직을 확률에 맡기면 검증이 불가능하다.

## 완료 판정

| # | 기준 | 검증 방법 |
|---|---|---|
| 1 | `paymentNo`로 조회하면 게이트웨이 대조에 필요한 값이 전부 나온다 | 응답 필드 검증 |
| 2 | 실패 건 조회 시 재시도 가능 여부를 알 수 있다 | `retriable` 필드 |
| 3 | 상태별, 기간별 목록 조회가 동작한다 | 통합 테스트 |
| 4 | `UNKNOWN` 건을 재조회해 `COMPLETED` 또는 `FAILED`로 확정한다 | 통합 테스트 |
| 5 | `UNKNOWN`이 아닌 건에 확정을 호출하면 상태가 변하지 않는다 | 통합 테스트 |
| 6 | **장애 주입을 켜면 확률만큼 실패가 섞인다** | 시드 고정 난수로 결정론적 검증 |
| 7 | **접두어로 지정한 시나리오는 확률과 무관하게 그대로 나온다** | 카오스 켠 상태에서 `TIMEOUT-` 호출 |
| 8 | 스케줄러가 `UNKNOWN` 건을 자동으로 확정 시도한다 | 통합 테스트 |

기준 6과 7이 짝이다. 확률적 실패가 실제로 발생해야 하지만, 의도한 시나리오까지 확률에 휘둘리면 나머지 테스트가 전부 불안정해진다.
