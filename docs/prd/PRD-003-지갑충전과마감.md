# PRD-003. 지갑 충전과 제출 마감

| 항목 | 값 |
|---|---|
| 상태 | **진행 중** — 지갑 충전 완료, 제출 마감(README·`.http`) 남음 |
| 선행 | [PRD-002](PRD-002-조회와정합성.md) |
| 대응 스펙 | [SPEC](../SPEC.md) §5.6 지갑 충전, §8.4 아키텍처 테스트, §10 산출물 |

---

## 무엇을 왜 만드나

두 가지를 한 사이클로 묶는다. 남은 기능 요구 하나와 제출 준비다.

### 지갑 충전

명세 2번의 마지막 문장이다.

> "고객 지갑은 결제 API 연동을 통해 **충전/차감**이 가능해야 합니다."

차감은 결제(PRD-001)가 담당했지만 **충전은 아직 구현되지 않았다.** 이 요구는 PRD 초안 작성 시 기능 요구사항 목록에서 누락됐고, SPEC 작성 중 명세 원문을 다시 읽으며 발견했다.

선불 지갑 모델에서 충전은 결제만큼 중요하다. 잔액이 어디서 생기는지 없이 차감만 있으면 시스템이 닫히지 않는다.

### 제출 준비

과제는 제출되어야 완료된다. 평가자가 클론해서 실행하고 눌러볼 수 있는 상태를 만든다.

## 이 사이클이 풀어야 하는 문제

**충전에도 멱등성이 필요하다.** 결제와 같은 이유다. 응답이 유실되면 클라이언트는 재시도하고, 그때 두 번 충전되면 없던 돈이 생긴다. 차감보다 오히려 위험하다. 차감은 잔액 부족으로 막히기라도 하지만 충전은 막는 장치가 없다.

**그리고 검증되지 않은 채 남은 규칙들이 있다.** 도메인이 인프라에 의존하지 않는다, 서비스가 리포지토리를 직접 잡지 않는다 같은 규칙은 지금까지 문서로만 존재했다. ArchUnit으로 강제하지 않으면 다음 사람이 어긴다.

## 범위

**포함**

- `POST /api/v1/wallets/{walletId}/charge` — 충전
- 충전 이력 저장 (V3 스키마)
- 충전 멱등 처리
- ArchUnit 아키텍처 테스트
- `README.md` — 실행 방법, API 목록, 설계 요약, 확장 로드맵
- `http/*.http` — 정상 경로와 오류 시나리오 전부
- 시나리오 매트릭스 9건 전수 검증 확인

**제외**

| 항목 | 이유 |
|---|---|
| 실제 충전 수단 연동(계좌이체·카드) | 과제의 외부 연동 대상은 결제 승인이다 |
| 환전 로직 | 과제 범위 밖 |
| 멀티 모듈 분리 | [SPEC](../SPEC.md) §10.1 트리거 조건 참조 |

## 완료 판정

| # | 기준 | 검증 방법 |
|---|---|---|
| 1 | 충전 후 잔액이 정확히 증가한다 | 통합 테스트 |
| 2 | 동일 `chargeNo` 재요청이 이중 충전하지 않는다 | 동시성 테스트 |
| 3 | 충전 이력이 조회 가능하다 | 통합 테스트 |
| 4 | 아키텍처 규칙 위반이 없다 | ArchUnit |
| 5 | 시나리오 9건이 전부 통과한다 | 통합 테스트 |
| 6 | **클론 후 한 줄로 실행된다** | 깨끗한 디렉터리에서 실제 실행 |
| 7 | README의 모든 주장이 코드로 확인된다 | 자기 검토 |

기준 6과 7이 마감의 실질이다. 특히 7은 과거 과제 리뷰에서 "README 주장과 코드 대조"가 실제 리뷰 방식이었음을 확인했기 때문에 둔다. 뒷받침할 수 없는 문장은 쓰지 않는다.

## 열린 질문

| # | 질문 | 진행 방식 |
|---|---|---|
| 1 | 충전 이력을 별도 테이블로 둘 것인가, `payment`에 유형 컬럼을 둘 것인가 | **결정: 별도 테이블(`wallet_charge`).** `payment` 14개 컬럼 중 6개가 게이트웨이 전용이라 충전이 쓰면 전부 NULL이 된다. 도메인도 `Payment`의 절반이 호출 불가능해진다. 상세는 [SPEC §5.6](../SPEC.md) |
| 2 | 충전에 통화 불일치가 오면 | 거부한다. 환전은 범위 밖이다 |
| 3 | README에 성능 수치를 쓸 것인가 | 쓰지 않는다. 부하 테스트를 하지 않았으므로 측정하지 않은 것을 주장하지 않는다 |

## 진행 기록

### 지갑 충전 — 완료 (2026-08-12)

`POST /api/v1/wallets/{walletId}/charge`. 이력은 `wallet_charge` 테이블(V3)에 남긴다.

구현하며 확정한 것 두 가지다.

**`status` 컬럼을 두지 않았다.** 결제의 `PENDING`은 "요청은 보냈는데 결과를 모른다"를 표현하려고 존재한다. 충전은 외부 호출이 없어 이력 기록과 잔액 증가가 한 트랜잭션에서 끝나므로 그 상태가 만들어질 수 없다. 넣었다면 항상 같은 값인 컬럼이 됐다.

**중복 요청을 409가 아니라 200으로 응답한다.** 결제는 처리 중인 건이 있어 409가 성립했지만, 충전은 성공했거나 행이 없거나 둘 뿐이다. 같은 요청에 같은 응답을 주는 것이 멱등의 정의에 맞고, 재시도한 호출자가 성공 여부를 다시 조회하지 않아도 된다.

검증에서 확인한 것: **UNIQUE 제약을 제거하자 동시 중복 테스트만 실패했다.** 선조회는 대부분을 거르지만 동시 요청에서는 둘 다 "없음"을 보고 통과하므로, 실제 직렬화 지점은 `uk_wallet_charge_no`다. 결제(ADR 0002)와 같은 구조이며 이번에 그 방어선이 작동함을 증명했다.

이력 조회 API는 넣지 않았다. 명세 §3-2는 충전 **실행**만 요구하고, 모니터링 요구(§3-1)는 결제 이력에 대한 것이다. 이력은 감사 추적으로 남기되 확인은 잔액 조회로 한다.
