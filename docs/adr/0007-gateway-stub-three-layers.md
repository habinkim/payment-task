# 0007. 게이트웨이 스텁은 용도에 따라 세 층으로 나눈다

상태: Accepted

## 맥락

과제의 외부 결제 API는 "가상의 3rd party"다. 실존하지 않으므로 우리가 만들어야 한다.

만드는 방법은 하나가 아니다. `PaymentGatewayClient` 인터페이스의 다른 구현체를 두어 자바 객체 레벨에서 갈아끼울 수도 있고, HTTP 엔드포인트를 띄워 실제 통신을 하게 할 수도 있다. 어느 쪽이든 "외부 결제를 모사한다"는 목적은 달성된다.

문제는 검증 범위가 다르다는 것이다.

검증해야 할 시나리오는 아홉 가지다([PRD §8.2](../PRD.md)). 이 중 정상 승인, 승인 거절, 잔액 부족, 중복 요청 네 가지는 응답 본문만 다르므로 어느 방식으로도 검증된다.

나머지 다섯 가지는 그렇지 않다. 500 응답, 400 응답, 타임아웃, 연결 실패, 지연 응답은 전부 **HTTP 계층에서 일어나는 일**이다.

특히 타임아웃이 문제다. 인터페이스 구현체가 `TimeoutException`을 던지는 것은 "타임아웃이 났다고 내가 선언한 것"이지 실제 타임아웃이 아니다. HTTP 클라이언트의 read timeout을 30초로 잘못 설정해도, 혹은 아예 설정하지 않아도 이 테스트는 통과한다. 검증하려던 대상이 검증되지 않는다.

타임아웃 처리는 [0004](0004-timeout-is-indoubt.md)의 핵심이다. 그 결정이 실제로 동작하는지 확인할 수 없다면 문서만 남는다.

한편 반대 방향의 문제도 있다. 모든 테스트를 HTTP로 하면 단위 테스트가 느려진다. 서비스의 상태 전이 로직을 검증하는 데 HTTP 서버를 띄울 이유가 없다.

그리고 평가자가 앱을 클론해 실행했을 때 결제가 동작해야 한다. 외부 게이트웨이가 실존하지 않으므로 무언가는 응답해야 한다.

## 결정

용도가 다르므로 세 층으로 나눈다. 하나의 스텁이 세 가지 목적을 모두 만족시키려 하지 않는다.

| 층 | 구현 | 용도 | 검증 대상 |
|---|---|---|---|
| `MockPaymentGatewayClient` | `PaymentGatewayClient` 인터페이스 구현체 | 단위 테스트 | 서비스 로직, 상태 전이, 실패 분류 |
| `StubGatewayController` | 앱 내부 HTTP 엔드포인트 | 자족 실행, 수동 검증 | 평가자가 앱만 띄워도 전 경로 동작 |
| WireMock | 테스트 전용 HTTP 서버 | 통합 테스트 | 타임아웃, 연결 실패, 상태 코드 처리 |

`MockPaymentGatewayClient`는 빠르다. HTTP를 타지 않으므로 단위 테스트가 밀리초 단위로 끝난다. 서비스가 승인 결과에 따라 올바른 상태로 전이하는지, 실패를 재시도 가능 여부로 옳게 분류하는지를 여기서 검증한다.

`StubGatewayController`는 같은 애플리케이션 안의 HTTP 엔드포인트다. 프로파일로 활성화한다. 평가자가 `docker compose up` 후 `.http` 파일로 결제를 호출하면 이것이 응답한다. 외부 의존 없이 전 경로가 동작하는 것이 목적이다.

WireMock은 테스트 스코프 의존성이다. 통합 테스트에서만 기동한다. `withFixedDelay()`로 지연을 만들고 `withFault(CONNECTION_RESET_BY_PEER)`로 연결을 끊는다. 이런 조작은 인터페이스 구현체로는 재현할 수 없고, 앱 내부 컨트롤러로 하면 톰캣 스레드를 붙잡는 부작용이 생긴다.

### 시나리오 트리거 규약

세 층이 같은 방식으로 시나리오를 지정해야 혼란이 없다. **`paymentNo` 접두어**로 통일한다.

```
TIMEOUT-20260810-001    무응답
ERR500-20260810-001     500 응답
ERR400-20260810-001     400 응답
DECLINE-20260810-001    승인 거절
SLOW-20260810-001       지연 응답
(접두어 없음)            정상 승인
```

`paymentNo`는 3rd party가 자유롭게 만드는 값이므로([0002](0002-payment-no-as-idempotency-key.md)) 요청 스펙을 바꾸지 않고 시나리오를 지정할 수 있다. 값이 원장에 그대로 남아 어떤 조건에서 만들어진 건인지 추적된다.

**접두어는 스텁만 해석한다.** `HttpPaymentGatewayClient`는 접두어의 존재를 알지 못하며, 받은 `paymentNo`를 그대로 외부에 전달할 뿐이다. 테스트 규약이 운영 코드로 새어 들어가지 않게 하는 경계다.

## 결과

아홉 개 시나리오가 전부 실제로 검증된다. 타임아웃 설정값이 틀리면 통합 테스트가 실패한다.

단위 테스트가 빠르게 유지된다. HTTP가 필요한 검증만 통합 테스트로 올라간다.

평가자가 외부 의존 없이 앱을 실행하고 모든 경로를 눌러볼 수 있다.

대신 **스텁 구현이 세 벌이 되었다.** 응답 형식이 바뀌면 세 곳을 고쳐야 한다. 이를 줄이기 위해 응답 DTO와 시나리오 판정 로직은 공유하고, 각 층은 그것을 어떻게 전달하느냐만 다르게 한다. 시나리오 접두어를 해석하는 코드는 한 곳에 둔다.

**의존성이 하나 늘었다.** WireMock은 테스트 스코프이므로 운영 산출물에는 포함되지 않고 운영 복잡도를 더하지 않는다. 되돌리기 쉬운 결정이라 도입 게이트를 간소하게 적용했다.

## 검토한 대안

- **인터페이스 구현체 하나로 전부 처리한다.** 가장 단순하고 의존성도 늘지 않는다. 그러나 HTTP 계층 시나리오 다섯 가지가 흉내에 그친다. 특히 타임아웃 설정이 검증되지 않아 0004의 결정이 문서로만 남는다.
- **앱 내부 스텁 컨트롤러 하나로 전부 처리한다.** 실제 HTTP를 타므로 검증 범위는 넓지만, 단위 테스트에서도 서버를 띄워야 해 피드백이 느려진다. 타임아웃 테스트는 스텁이 톰캣 스레드를 붙잡고 있어야 해서 테스트끼리 간섭할 수 있다.
- **WireMock 하나로 전부 처리하고 앱 내부 스텁을 두지 않는다.** 테스트는 충실해지지만 평가자가 앱을 실행했을 때 결제할 대상이 없다. 자족 실행을 해친다. 별도로 WireMock을 띄워달라고 요구하는 것은 평가 편의를 떨어뜨린다.
- **실제 PG의 샌드박스를 연동한다.** 가장 현실적인 검증이 되지만 과제가 요구한 것은 가상의 3rd party이고, 외부 서비스에 의존하면 네트워크 없이는 테스트가 돌지 않는다.
