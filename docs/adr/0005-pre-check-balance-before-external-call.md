# 0005. 명세 시퀀스를 지키되 잔액 사전검증을 추가한다

상태: Accepted

## 맥락

과제가 제시한 시퀀스 다이어그램의 순서는 다음과 같다.

```
① 결제 원장 PENDING 저장
② 외부 결제 승인 요청
③ 고객 지갑 잔액 확인
④ 충분하면 차감 → COMPLETED / 부족하면 FAILED (INSUFFICIENT_BALANCE)
```

②에서 승인이 났다는 것은 외부 원장에서 이미 돈이 움직였다는 뜻이다. 그런데 ③에서 잔액이 부족하다고 판명되면 ④에서 실패로 처리한다. 결과는 **외부는 성공, 내부는 실패**다.

선불 충전형 지갑에서 이 순서는 특히 어색하다. 지갑에 100 USD가 있는데 150 USD 결제를 외부에 먼저 승인 요청하는 것 자체가 성립하기 어렵다. 잔액은 결제가 시작될 수 있는지를 가르는 선행 조건이지, 승인을 받아온 뒤에 확인할 대상이 아니다.

한편 명세는 재량도 열어두었다. "과제 진행 시 명시되지 않은 인증, 권한, 세부 정책은 지원자님의 판단에 따라 자유롭게 설계해 주세요."

그리고 다이어그램 하단의 Note는 정합성을 명시적으로 요구한다. "지갑 잔액 확인, 금액 차감, 결제 이력 저장은 트랜잭션으로 처리하여 금액 정합성을 보장한다."

여기서 판단이 필요하다. 명세를 그대로 구현할 것인가, 순서를 바꿀 것인가.

## 결정

**명세 시퀀스를 기준 구현으로 채택하고, 외부 호출 직전에 잔액 사전검증을 한 단계 추가한다.**

```
① 결제 원장 PENDING 저장
② [추가] 잔액 사전검증 — 부족하면 즉시 실패, 외부를 호출하지 않는다
③ 외부 결제 승인 요청
④ 잔액 재확인 + 원자적 차감          ← 명세의 ③④를 그대로 유지
⑤ COMPLETED
```

②는 명세를 대체하지 않는다. 명세의 잔액 확인과 차감은 ④에 그대로 남아 있고, 그 앞에 방어선을 하나 더 두는 것이다. 요구사항에서 빼는 것 없이 더하기만 한다.

사전검증은 읽기 전용이다. 잔액을 조회해 결제 금액과 비교하고, 부족하면 `INSUFFICIENT_BALANCE`로 실패시킨다. 이 경로에서는 외부 호출이 아예 일어나지 않으므로 미아 거래가 생길 수 없다.

④의 차감은 조건부 UPDATE로 원자화한다([0003](0003-atomic-balance-deduction.md)). 사전검증을 통과했더라도 차감 시점에 다시 검사한다. 사전검증은 최적화이지 보증이 아니다.

## 결과

미아 거래의 대다수 경로가 사라진다. 잔액이 애초에 부족한 결제는 외부에 도달하지 않는다.

불필요한 외부 호출이 줄어든다. 실패할 것이 확정된 요청을 PG에 보내지 않으므로, 외부 API 호출 비용과 지연이 절약된다. 부수적이지만 실제 서비스에서는 무시할 수 없는 이득이다.

대신 **경쟁 조건이 완전히 사라지지는 않는다.** ②에서 잔액이 충분했는데 ③이 진행되는 동안 다른 결제가 잔액을 소진하면, ④에서 차감이 실패한다. 이때는 외부 승인이 이미 난 상태이므로 미아 거래가 된다.

이 잔여 경로를 다음과 같이 다룬다.

- 발생을 인정하고 `INSUFFICIENT_BALANCE`로 실패 처리하되, 외부 승인이 났다는 사실을 원장에 남긴다(외부 거래 식별자 기록).
- 이 조합(외부 승인됨 + 내부 실패)을 **별도 카운터로 집계**한다. 조용히 넘어가지 않는다.
- 보상 취소 호출은 v1에서 구현하지 않는다. 취소 API 명세가 과제에 없고, 임의로 만들면 검증할 수 없다. 대신 운영자가 인지할 수 있게 기록과 지표를 남긴다.

시나리오 테스트에는 이 경로를 남겨둔다. 사전검증 때문에 정상 흐름에서는 도달하지 않지만, 경쟁 조건에서의 동작을 검증하려면 필요하다.

**명세보다 한 단계 많은 구현이 되었다.** 이것이 요구사항 이탈로 읽히지 않도록 README에 관계를 명시한다. 명세의 시퀀스는 그대로 살아 있고, 추가된 것은 그 앞의 fail-fast라는 점을 분명히 한다.

## 검토한 대안

- **명세를 한 글자도 벗어나지 않고 그대로 구현한다.** 요구사항 충실도 관점에서 가장 안전하고, 순서 문제는 문서로만 지적하는 방식이다. 그러나 잔액이 명백히 부족한 요청까지 외부에 보내게 되고, 발생이 예상되는 미아 거래를 알면서 방치하는 셈이 된다. 결제 시스템에서 취하기 어려운 태도다.
- **선점(hold) 방식으로 재설계한다.** ①에서 잔액을 선점해 묶어두고, 외부 승인이 성공하면 확정 차감하고 실패하면 해제한다. 미아 거래가 구조적으로 불가능해지는 가장 올바른 설계다. 다만 명세 시퀀스와 흐름이 달라지고, 선점 만료 처리와 해제 실패 처리라는 새로운 실패 모드가 추가된다. 7일 과제에서 명세를 재설계하는 것은 요구사항 이해 항목에서 감점 위험이 크다. 확장 경로로 문서화한다.
- **잔액 확인만 앞으로 옮기고 차감은 뒤에 둔다.** 사실상 채택한 안과 같지만, 명세의 ③을 삭제하고 앞으로 이동시키는 형태다. 명세 항목을 제거하는 모양이 되므로, 유지하면서 추가하는 쪽을 택했다.
- **외부 승인 후 잔액 부족이면 즉시 취소 API를 호출한다.** 보상 트랜잭션으로 되돌리는 방식이다. 취소 API 명세가 과제에 주어지지 않아 임의로 정의해야 하고, 취소 자체의 실패를 다시 처리해야 한다. 근본적으로는 발생을 막는 편이 되돌리는 편보다 낫다.
