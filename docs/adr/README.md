# 아키텍처 결정 기록 (ADR)

이 디렉터리는 결제 시스템을 설계하면서 내린 주요 결정과 그 이유를 남긴다. 다이어그램과 코드는 "어떻게"만 보여주기 때문에, "왜 이렇게 했는지"는 여기에 따로 적어 둔다. 나중에 같은 고민을 처음부터 반복하지 않으려는 목적이다.

문서는 맥락, 결정, 결과(트레이드오프), 검토한 대안 순서로 쓴다. 결정이 바뀌면 기존 문서를 지우지 않고 새 ADR로 대체하며 상태를 `Superseded`로 표시한다.

| 번호 | 제목 | 상태 |
|------|------|------|
| [0001](0001-external-call-outside-transaction.md) | 외부 결제 호출은 트랜잭션 밖에서 수행한다 | Accepted |
| [0002](0002-payment-no-as-idempotency-key.md) | 결제번호는 3rd party가 생성하고 멱등 키를 겸한다 | Accepted |
| [0003](0003-atomic-balance-deduction.md) | 잔액 차감은 조건부 UPDATE로 원자화한다 | Accepted |
| [0004](0004-timeout-is-indoubt.md) | 타임아웃은 실패가 아니라 결과 미상으로 다룬다 | Accepted |
| [0005](0005-pre-check-balance-before-external-call.md) | 명세 시퀀스를 지키되 잔액 사전검증을 추가한다 | Accepted |
| [0006](0006-single-server-no-middleware.md) | 단일 서버로 시작하고 미들웨어를 도입하지 않는다 | Accepted |

## 결정들의 관계

여섯 개의 결정은 독립적이지 않다. 하나의 문제의식에서 갈라져 나왔다.

외부 결제사와 우리 지갑은 서로 다른 두 개의 원장이고, 이 둘에 걸친 원자성은 단일 트랜잭션으로 확보할 수 없다. 외부 API 호출은 롤백되지 않기 때문이다. 나머지 결정은 이 제약을 어떻게 다룰 것인가에 대한 답이다.

- 0001은 트랜잭션 경계를 어디에 그을지 정한다. 외부 호출을 밖으로 빼내 장애 전파를 막는다.
- 0005는 애초에 실패할 결제가 외부에 도달하지 않게 막는다. 문제를 예방하는 쪽이다.
- 0003은 내부 원장 안에서의 정합성을 보장한다. 잔액이 음수가 되지 않게 한다.
- 0004는 그럼에도 결과를 알 수 없는 경우를 다룬다. 모르는 것을 안다고 기록하지 않는다.
- 0002는 재시도가 안전하도록 만든다. 결과를 모르면 클라이언트는 다시 보내기 때문이다.
- 0006은 위 다섯 가지를 미들웨어 없이 해결할 수 있음을 확인하고, 도입 조건을 미리 정해둔다.

- 0007은 위 결정들이 실제로 동작하는지 검증할 수단을 정한다. 외부가 실존하지 않으므로 검증 환경을 우리가 만들어야 한다.

0002와 0004는 특히 맞물려 있다. 타임아웃 건을 조회로 확정하려면 클라이언트가 조회 키를 알고 있어야 하고, 그것은 서버가 발급한 번호로는 불가능하다.

0004와 0007도 마찬가지다. 타임아웃을 결과 미상으로 다루겠다는 결정은, 실제 타임아웃을 만들어낼 수 있어야 검증된다. 인터페이스 구현체가 예외를 던지는 것으로는 타임아웃 설정이 옳은지 알 수 없다.
