# 아키텍처 결정 기록 (ADR)

이 디렉터리는 결제 시스템을 설계하면서 내린 주요 결정과 그 이유를 남긴다. 다이어그램과 코드는 "어떻게"만 보여주기 때문에, "왜 이렇게 했는지"는 여기에 따로 적어 둔다. 나중에 같은 고민을 처음부터 반복하지 않으려는 목적이다.

문서는 맥락, 결정, 결과(트레이드오프), 검토한 대안 순서로 쓴다. 결정이 바뀌면 기존 문서를 지우지 않고 새 ADR로 대체하며 상태를 `Superseded`로 표시한다.

|------|------|------|

| [0002](0002-payment-no-as-idempotency-key.md) | 결제번호는 3rd party가 생성하고 멱등 키를 겸한다 | **Superseded by 0011** |

## 결정들의 관계

열두 개의 결정은 독립적이지 않다. 하나의 문제의식에서 갈라져 나왔다.

외부 결제사와 우리 지갑은 서로 다른 두 개의 원장이고, 이 둘에 걸친 원자성은 단일 트랜잭션으로 확보할 수 없다. 외부 API 호출은 롤백되지 않기 때문이다. 나머지 결정은 이 제약을 어떻게 다룰 것인가에 대한 답이다.

- 0001은 트랜잭션 경계를 어디에 그을지 정한다. 외부 호출을 밖으로 빼내 장애 전파를 막는다.
- 0005는 애초에 실패할 결제가 외부에 도달하지 않게 막는다. 문제를 예방하는 쪽이다.
- 0003은 내부 원장 안에서의 정합성을 보장한다. 잔액이 음수가 되지 않게 한다.
- 0004는 그럼에도 결과를 알 수 없는 경우를 다룬다. 모르는 것을 안다고 기록하지 않는다.
- 0002는 재시도가 안전하도록 만든다. 결과를 모르면 클라이언트는 다시 보내기 때문이다.
- 0006은 위 다섯 가지를 미들웨어 없이 해결할 수 있음을 확인하고, 도입 조건을 미리 정해둔다.
- 0007은 실존하지 않는 외부를 무엇으로 대신할지 정한다. 모의 구현이 곧 정상 동작 경로이므로 운영 코드에 둔다.
- 0008은 그 결정들을 담는 도메인 객체를 영속화 요구로부터 지킨다. JPA가 기본 생성자를 요구하므로 엔티티를 분리한다.
- 0012는 0003이 잔액에 적용한 조건부 UPDATE를 상태 전이에도 적용한다. 차감만 원자적이고 상태 전이는 무조건 덮어쓰기였던 비대칭이 이중 차감으로 드러났다.
- 0011은 0002의 이름을 바로잡는다. 우리가 게이트웨이인데 `PaymentGatewayClient`·`paymentNo`가 역할을 거꾸로 가르쳤다. 결정의 골자는 0002 그대로다.
- 0010은 0008이 그은 경계를 한 겹 위로 올린다. 0008이 도메인 객체를 엔티티로부터 지켰다면, 0010은 서비스를 영속 기술로부터 지킨다. 저장소의 계약을 도메인이 정의하고 구현만 인프라에 둔다.
- 0009는 0007의 검증 방식을 대체한다. 실제 게이트웨이가 없어 HTTP 계층 검증이 성립하지 않으므로, 확률 기반 장애 주입으로 실패 상황 자체를 만든다.

0002와 0004는 특히 맞물려 있다. 타임아웃 건을 조회로 확정하려면 클라이언트가 조회 키를 알고 있어야 하고, 그것은 서버가 발급한 번호로는 불가능하다.

0004와 0007도 마찬가지다. 타임아웃을 결과 미상으로 다루겠다는 결정은 실제 타임아웃을 만들어낼 수 있어야 검증된다. 모의 구현이 결과 미상을 반환하는 것만으로는 타임아웃 설정이 옳은지 알 수 없어, 0007은 검증 책임을 모의 구현과 WireMock으로 나눈다.
