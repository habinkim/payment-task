# 0002. 결제번호는 3rd party가 생성하고 멱등 키를 겸한다

상태: **Superseded by [0011](0011-merchant-payment-no.md)** — 결정의 골자(3rd party가 발급하고 멱등 키를 겸한다)는 유효하나, 필드명이 `paymentNo`에서 `merchantPaymentNo`로 바뀌었다.

## 맥락

결제 API는 재시도되는 API다. 응답이 오지 않으면 클라이언트는 다시 보낸다. 그것이 정상적인 행동이고, 막을 수도 없다. 따라서 서버는 같은 결제가 두 번 처리되지 않도록 스스로를 지켜야 한다.

중복을 판정하려면 "같은 요청"을 식별할 키가 필요하다. 여기서 키를 누가 만드느냐가 갈림길이다.

서버가 결제번호를 발급하는 방식이 언뜻 자연스러워 보인다. 주문번호나 거래번호는 보통 시스템이 채번한다. 그러나 재시도 시나리오를 따라가면 성립하지 않는다는 것이 드러난다.

3rd party가 결제를 요청했는데 응답이 오지 않았다. 타임아웃이다. 이 시점에 3rd party가 가진 것은 무엇인가. **서버가 발급한 번호는 받지 못했다.** 응답이 유실됐기 때문이다. 그런데 재시도해야 한다. 무엇으로 "이건 아까 그 요청과 같은 건이다"라고 주장할 것인가.

서버 발급 번호로는 답이 없다. 클라이언트가 처음부터 들고 있던 값이어야만 한다.

조회도 같은 구조다. `GET /payments/{id}`처럼 서버 PK로 조회하게 만들면, 결제 응답을 받아야만 조회할 수 있다. 그런데 조회가 가장 절실한 상황이 바로 응답을 못 받은 타임아웃이다. 정작 필요할 때 쓸 수 없는 API가 된다.

## 결정

**결제번호(`paymentNo`)를 3rd party가 생성해 요청과 함께 보낸다.** 서버는 이 값에 UNIQUE 제약을 걸어 중복 처리를 차단하고, 조회 키로도 사용한다.

```sql
payment_no VARCHAR(64) NOT NULL,
CONSTRAINT uk_payment_no UNIQUE (payment_no)
```

동일 `paymentNo`로 재요청이 오면 새로 처리하지 않고 **최초 결과를 그대로 반환**한다. 제약 위반을 잡아 기존 건을 조회해 돌려주는 방식이다. 단순히 에러를 내면 클라이언트는 여전히 결과를 모른다.

형식은 다음과 같이 제한한다.

| 항목 | 값 | 이유 |
|---|---|---|
| 타입 | `VARCHAR(64)` | UNIQUE 인덱스 크기를 제한한다. 길이가 무제한이면 인덱스 비용이 커진다 |
| 문자셋 | 영숫자와 하이픈 | URL 경로와 로그에 그대로 쓰이므로 이스케이프가 필요 없어야 한다 |
| 유일성 범위 | 전역 | 단일 3rd party 연동을 가정한다 |

서버 PK(`id`)는 외부에 노출하지 않는다. auto-increment 값이 응답에 실리면 누적 결제 건수를 추정할 수 있다.

이름을 `idempotencyKey`가 아니라 `paymentNo`로 정한 것은 의도적이다. 필드가 하는 일(중복 차단)이 아니라 필드가 무엇인지(결제번호)를 이름에 담는다. 구현 메커니즘을 이름에 박아 넣으면, 나중에 그 필드가 조회 키로도 쓰이게 됐을 때 이름이 거짓말을 한다.

## 결과

타임아웃 후 재시도가 안전해진다. 몇 번을 보내도 차감은 한 번이다.

조회가 클라이언트 쪽에서 항상 가능해진다. 3rd party는 자기가 만든 번호를 언제나 알고 있으므로, 응답을 받지 못한 상태에서도 `GET /payments/{paymentNo}`를 호출할 수 있다. 이것이 [0004](0004-timeout-is-indoubt.md)의 결과 미상 확정 절차가 성립하는 전제다.

대신 **번호의 유일성을 클라이언트에 의존한다.** 3rd party가 번호를 재사용하면 서로 다른 결제가 중복으로 판정된다. 이것은 API 계약으로 명시하고 문서화하는 수밖에 없다. 서버가 강제할 수 있는 것은 형식뿐이다.

또한 연동 3rd party가 둘 이상이 되면 전역 UNIQUE가 오작동한다. A사와 B사가 각각 `ORDER-001`을 쓰면 서로 다른 결제인데 충돌한다. 현재 명세에 가맹점 개념이 없어 단일 연동을 가정했고, 다중이 되는 시점에 `(merchantId, paymentNo)` 복합 키로 전환한다.

## 검토한 대안

- **서버가 결제번호를 발급한다.** 채번 방식으로는 자연스럽지만 멱등 키로 쓸 수 없다. 타임아웃 재시도 시점에 클라이언트가 그 번호를 모르기 때문이다.
- **클라이언트 멱등 키와 서버 결제번호를 별도 필드로 둔다.** 토스페이먼츠(`orderId` + `paymentKey`)나 스트라이프(`Idempotency-Key` 헤더 + `pi_xxx`)가 쓰는 방식이고, 규모가 커지면 이쪽이 맞다. 다만 이번 과제 범위에서는 필드가 둘로 늘어난 만큼의 이득이 없다. 단일 연동이고 조회 키와 멱등 키를 겸해도 충돌하지 않는다.
- **요청 본문 전체를 해시해 멱등 키로 쓴다.** 클라이언트가 키를 관리하지 않아도 된다는 장점이 있지만, 금액이 같은 별개의 정상 결제가 중복으로 판정된다. 같은 가맹점에서 같은 금액을 두 번 결제하는 것은 흔한 일이다.
- **분산 락으로 중복 요청을 직렬화한다.** 락이 풀린 뒤 들어온 재시도는 여전히 중복 처리된다. 락은 동시성을 다루는 도구이지 멱등성을 주는 도구가 아니다.
