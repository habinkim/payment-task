# 0006. 단일 서버로 시작하고 미들웨어를 도입하지 않는다

상태: Accepted

## 맥락

결제 시스템이라는 주제는 확장 관련 기술을 끌어들이기 쉽다. 큐로 요청을 흡수하고, 캐시로 조회를 받고, 분산 락으로 동시성을 다루고, 이벤트를 발행해 정산과 알림을 붙이는 그림이 자연스럽게 떠오른다.

그러나 이번 과제의 요구사항은 다음이 전부다. 결제 API를 제공하고, 원장을 `PENDING`으로 저장하고, 외부 승인을 확인하고, 잔액을 차감하고, 실패 사유를 남긴다.

여기에 미들웨어가 필요한 지점이 있는지 하나씩 따져야 한다. 추측으로 도입하면 복잡도만 늘고, 그 복잡도는 평가에서 이해도 부족으로 읽힌다.

판단 기준을 미리 정한다. **새 기술은 기본값이 도입하지 않음이다.** 기존 스택의 한계를 수치나 현상으로 정의하고, 대안을 소진하고, 그래도 남을 때 도입한다.

## 결정

**v1은 단일 Spring Boot 애플리케이션과 인메모리 H2로 구성한다.** 외부 결제 API는 운영 코드의 모의 구현으로 모사한다([0007](0007-mock-gateway-in-production.md)).

DB는 선택이 아니라 명세가 정했다. "지원자에게 별도 DB가 제공되지 않으므로 In-Memory DB(H2) 또는 Local DB(SQLite) 등을 활용해 주세요." 둘 중 H2를 택한 이유는 Hibernate가 공식 방언을 제공하고 Flyway가 별도 모듈 없이 지원하기 때문이다. SQLite는 Hibernate 공식 방언이 없어 커뮤니티 모듈을 더해야 하고, 쓰기를 직렬화하는 특성이 있어 동시성 검증에 제약이 생긴다.

각 미들웨어를 기각한 근거는 다음과 같다.

**메시지 큐(Kafka)를 도입하지 않는다.** 결제는 동기 응답이 필수다. 3rd party는 승인 여부를 즉시 알아야 하므로 큐에 넣고 나중에 처리할 수 없다. 결제 완료 이벤트를 소비할 대상도 현재 없다. 소비자가 없는 큐는 복잡도만 더한다.

**캐시와 분산 락(Redis)을 도입하지 않는다.** 조회는 `merchantPaymentNo` 단건과 목록 페이징뿐이라 B-tree 인덱스로 충분하다. 정렬 집합이나 순위 연산이 없다. 분산 락도 필요 없다. 단일 서버에서 잔액 동시성은 DB 조건부 UPDATE로 해결된다([0003](0003-atomic-balance-deduction.md)).

**Saga 오케스트레이션을 도입하지 않는다.** 참여 대상이 지갑과 PG 둘뿐이다. 두 시스템 사이의 정합성은 상태 머신과 확정 절차([0004](0004-timeout-is-indoubt.md))로 다룰 수 있다. 오케스트레이터를 두면 관리 대상이 하나 더 생길 뿐이다.

**이벤트 소싱을 도입하지 않는다.** 결제 원장 테이블 자체가 이력이다. 상태 변경 이력이 필요하면 원장에 컬럼을 더하거나 이력 테이블을 붙이는 것으로 충분하다. 감사 요구가 상태 재구성 수준을 요구하지 않는다.

다만 **무상태 설계는 유지한다.** 세션이나 로컬 캐시에 상태를 두지 않는다. 인스턴스를 늘릴 때 코드 변경이 없도록 하는 것은 비용이 들지 않는 대비이므로 지금 해둔다. 하지 않는 것은 미들웨어 도입이지 확장 가능한 구조가 아니다.

도입 트리거를 미리 정의한다. 조건이 관측되면 그때 검토한다.

| 후보 | 트리거 |
|---|---|
| 분산 락 | 서버 다중화가 확정되고 DB 락 경합이 측정될 때 |
| 메시지 큐 | 결제 이벤트를 소비할 독립 서비스가 2개 이상 생길 때 |
| 아웃박스 | 이벤트 발행 유실이 실제로 관측될 때 |
| Saga | 참여 서비스가 3개 이상이 될 때 |
| 자동 대사 배치 | `UNKNOWN` 건이 수동 처리 한계를 넘을 때 |
| 읽기 복제본 | 조회 트래픽이 쓰기를 압도할 때 |
| 서킷 브레이커 | 외부 장애가 연쇄 지연을 유발할 때 |

트리거를 규모가 아니라 **사건**으로 적었다. "트래픽이 늘면"은 판단 기준이 되지 못한다. 무엇이 관측되면 도입하는지가 분명해야 나중에 같은 고민을 반복하지 않는다.

## 결과

구조가 단순해져 전 구간을 설명할 수 있다. 요청이 들어와 응답이 나가기까지의 경로에 추측으로 넣은 요소가 없다.

자족 실행이 쉬워진다. 외부 의존 컴포넌트가 아예 없어 평가자는 클론 후 `./gradlew bootRun` 한 줄로 띄울 수 있다. 도커도, 별도 DB 설치도 필요 없다.

대신 **인메모리라 재기동하면 데이터가 사라진다.** 결제 원장이 휘발되는 것은 실서비스라면 성립할 수 없지만, 평가용으로는 매 실행이 깨끗한 상태에서 시작한다는 이점이 있다. 실제 운영으로 간다면 DB 교체가 전제이며, Flyway 마이그레이션과 표준 SQL로 스키마를 정의해 두었으므로 교체 비용은 방언 설정 수준에 그친다.

테스트가 빨라진다. 컨테이너를 띄울 필요가 없어 통합 테스트도 인메모리 위에서 곧바로 돈다.

대신 **성능 한계를 실측하지 않은 채로 남겨둔다.** 이 구성이 어느 정도 부하까지 견디는지 이 과제에서는 측정하지 않는다. 부하 테스트 없이 "충분하다"고 주장하면 근거 없는 말이 되므로, 충분하다고 주장하는 대신 **요구사항에 부하 조건이 없다**는 사실을 명시한다. 성능 주장을 하지 않는 것이 측정 없이 주장하는 것보다 정직하다.

**서버를 늘리는 순간 잔액 동시성 방식을 재검토해야 한다.** 조건부 UPDATE는 단일 DB를 전제하므로 DB가 하나인 한 다중 인스턴스에서도 동작한다. DB를 샤딩하는 시점에는 이야기가 달라진다. 그 지점을 트리거 표에 남겨둔다.

## 전제가 깨지는 지점 (2026-08-12 검토 추가)

수평 확장을 가정하고 이 결정의 유효 범위를 확인했다. 실측한 것과 구조 분석으로 판정한 것을 구분해 적는다.

### 이 시스템의 정합성은 셋에 걸려 있다

| 보장 | 수단 |
|---|---|
| 멱등성 | `uk_merchant_payment_no` UNIQUE |
| 원자적 차감 | `UPDATE ... WHERE balance >= :amount` |
| 상태 전이 | `UPDATE ... WHERE status not in (terminal)` ([ADR 0012](0012-conditional-update-for-state-transition.md)) |

**셋 다 "한 대의 DB가 전역을 안다"는 가정 위에 있다.** JVM 락(`synchronized`, `ReentrantLock`)은 프로덕션 코드에 0건이라 "단일 서버에선 되는데 늘리면 조용히 깨지는" 함정은 피했지만, 분산 락으로 대체된 것도 아니므로 위 셋이 무너지면 보호가 없다.

### WAS만 늘릴 때 — 동작한다

DB가 한 대인 한 위 셋이 그대로 성립한다. 다만 **스케줄러가 인스턴스 수만큼 중복 실행된다.** `findOldestUnknown()`은 `created_at ASC` 정렬의 평범한 SELECT라 정렬이 결정적이고, 실측 결과 두 번 호출 시 **3/3 전부 같은 건을 집었다.** `application-prod.yaml`이 `payment.reconcile.enabled: true`를 박아두므로 prod로 N대를 띄우면 N개 스케줄러가 같은 배치를 돈다.

정합성은 ADR 0012의 조건부 UPDATE가 지킨다. 남는 것은 **게이트웨이 호출 낭비**이며, 그건 효율성 문제라 ShedLock 같은 수단으로 별도 판단한다.

### DB를 늘릴 때 — 전제가 무너진다

**읽기 복제.** `readOnly = true` 트랜잭션이 코드에 7곳 있다. Replica로 라우팅되면 복제 지연 때문에 `findOldestUnknown()`이 **이미 확정된 건을 UNKNOWN으로 착각**한다. ADR 0012의 CAS가 최종 방어를 하므로 정합성은 지켜지지만 헛일이 늘어난다.

**샤딩.** `uk_merchant_payment_no`가 **샤드별 인덱스**가 된다. 같은 결제번호가 다른 샤드에 들어가면 **멱등이 깨진다** — 지금 멱등 설계 전체가 이 제약 하나에 걸려 있다. `wallet_id`로 샤딩하면 결제의 `payment` INSERT와 `wallet` UPDATE가 크로스 샤드가 되어 분산 트랜잭션(2PC/Saga)이 필요해진다.

두 항목은 H2 인메모리라 **재현하지 못했다.** 구조 분석에 의한 판정이며 실측과 근거 등급이 다르다.

### 선결 과제 — prod도 인메모리다

`datasource` 정의가 `application.yaml` 한 곳뿐이고 `application-prod.yaml`에 오버라이드가 없다. 인메모리 DB는 JVM 프로세스에 종속되므로 **지금 3대를 띄우면 DB가 3개**다. 잔액도 원장도 인스턴스마다 갈라진다.

과제 명세가 H2/SQLite를 요구했으므로 결함은 아니다. 다만 수평 확장 논의가 성립하려면 공유 DB가 선결 조건이다.

### H2와 MySQL의 격리 수준이 다르다

동시성 테스트가 전부 H2 위에서 돈다. **H2는 READ COMMITTED, MySQL InnoDB는 REPEATABLE READ**다.

반직관적인 사실이 하나 있다. InnoDB RR에서 **plain SELECT는 non-locking snapshot read**라 락을 걸지 않으므로, `SELECT` 후 `UPDATE`하는 lost update를 **막지 못한다.** PostgreSQL RR은 first-updater-wins로 막는다. 격리 수준 기본값이 높다고 더 안전한 게 아니다([Percona](https://www.percona.com/blog/what-if-mysqls-repeatable-reads-cause-you-to-lose-money/), [Jepsen: MySQL 8.0.34](https://jepsen.io/analyses/mysql-8.0.34)).

이 때문에 ADR 0012에서 잡은 이중 차감은 MySQL에서 **더 잘 재현된다** — RR 스냅샷 때문에 경쟁 트랜잭션의 커밋을 볼 수 없기 때문이다. 수정 방향은 같지만, **H2에서 통과한 동시성 테스트가 MySQL에서 같다는 보장은 없다.** Testcontainers로 동시성 IT만 MySQL에서 돌리는 것이 다음 단계다.

## 검토한 대안

- **처음부터 확장 가능한 구성으로 만든다.** 나중에 옮기는 비용을 아낄 수 있다는 논리지만, 필요해지지 않으면 그 비용은 발생하지 않는다. 불확실한 미래를 위해 지금 복잡도를 지불하는 것은 손실이다. 과거 유사 과제에서 규모가 요구하지 않는 미들웨어를 넣어 감점 요인으로 자평한 경험이 있다.
- **일부만 도입한다(예: Redis만).** 하나만 넣으면 복잡도가 적다는 판단이지만, 그 하나가 필요한 근거가 여전히 없다. 개수가 아니라 필요 여부가 기준이다.
- **미들웨어 없이 만들되 인터페이스만 미리 추상화해 둔다.** 나중에 갈아 끼우기 쉽게 하려는 의도다. 캡슐 구조로 인프라 접근을 격리하는 것까지는 하되, 쓰지 않을 구현을 위한 추상화 계층은 만들지 않는다. 추상화는 두 번째 구현이 생길 때 그 모양을 보고 만드는 것이 정확하다. 다만 외부 게이트웨이 클라이언트만은 예외로 인터페이스를 둔다. 모의 구현과 실제 연동 구현이 둘 다 운영 코드에 존재하므로([0007](0007-mock-gateway-in-production.md)) 두 번째 구현이 이미 있는 경우에 해당한다.
