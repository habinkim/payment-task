# 0001. 외부 결제 호출은 트랜잭션 밖에서 수행한다

상태: Accepted

## 맥락

결제 한 건을 처리하려면 세 가지 쓰기가 필요하다. 결제 원장을 남기고, 외부 결제 API로 승인을 받고, 고객 지갑에서 금액을 차감한다. 이 중 두 번째는 우리 DB가 아니라 남의 시스템이다.

가장 단순한 구현은 셋을 하나의 `@Transactional` 메서드에 넣는 것이다. 그러면 실패했을 때 전부 롤백되니 정합성이 지켜질 것처럼 보인다. 그러나 두 가지가 무너진다.

첫째, **외부 호출은 롤백되지 않는다.** DB 트랜잭션이 롤백돼도 이미 나간 HTTP 요청은 되돌아오지 않는다. 외부에서 승인이 났다면 그 사실은 남는다. 트랜잭션으로 감싼다고 원자성이 생기지 않는데도 생긴 것처럼 착각하게 만든다.

둘째, **커넥션 점유 시간이 외부 응답 시간에 종속된다.** 외부 API가 3초 걸리면 DB 커넥션을 3초간 붙잡는다. 기본 커넥션 풀이 10개라고 하면, 동시 결제 4건만 들어와도 12초치 커넥션이 묶인다. 외부가 느려지는 순간 커넥션 풀이 고갈되고, 결제와 무관한 조회 API까지 함께 죽는다. 외부 장애가 전체 장애로 번지는 경로다.

과제 명세가 결제 원장을 `PENDING` 상태로 **먼저 저장하라**고 요구한 것이 이 문제와 맞닿아 있다. 단순 상태 표시라면 굳이 외부 호출 전에 저장할 이유가 없다.

## 결정

트랜잭션을 두 개로 나누고, 그 사이에서 외부를 호출한다.

```
[TX1] 결제 원장 PENDING 저장 → 커밋
      ↓
[트랜잭션 밖] 외부 결제 승인 요청
      ↓
[TX2] 잔액 차감 + 상태 확정 → 커밋
```

TX1이 커밋된 뒤에 외부를 호출하므로, 호출 도중 서버가 죽어도 "이 결제를 시도했다"는 사실이 DB에 남는다. Write-Ahead Intent Log와 같은 구조다. 남은 `PENDING` 건은 나중에 조회로 확정할 수 있다([0004](0004-timeout-is-indoubt.md)).

실제 연동 구현(`HttpPaymentGatewayClient`)에는 connect와 read 타임아웃을 모두 명시한다. 타임아웃이 없으면 커넥션을 트랜잭션 밖으로 뺀 의미가 절반으로 준다. 스레드는 여전히 무한정 묶이기 때문이다.

기본 프로파일의 모의 구현은 프로세스 안에서 응답하므로 이 설정이 적용되지 않는다([0007](0007-mock-gateway-in-production.md)). 타임아웃 설정이 실제로 동작하는지는 WireMock을 상대로 하는 통합 테스트에서 검증한다.

## 결과

외부 장애가 DB 커넥션 풀로 전파되지 않는다. 외부가 느려져도 묶이는 것은 요청 스레드뿐이고, 조회 API는 정상 동작한다.

대신 **TX1과 TX2 사이에 원자성이 없다.** TX1 직후 서버가 죽으면 `PENDING` 상태의 고아 레코드가 남는다. 이것을 결함이 아니라 설계된 상태로 다룬다. `PENDING`은 "처리 중이거나 결과를 모르는 건"을 의미하며, 조회로 확정하는 절차를 둔다.

트랜잭션이 둘로 갈리면서 코드에서 경계가 눈에 보이게 됐다. 한 메서드에 `@Transactional`을 붙이는 것보다 읽기는 번거롭지만, 어디까지가 원자적인지 착각할 여지가 없어진다.

## 검토한 대안

- **셋을 한 트랜잭션에 묶는다.** 가장 단순하지만 외부 호출은 롤백되지 않으므로 원자성은 착시다. 커넥션 고갈 위험까지 떠안으면서 얻는 것이 없다.
- **외부 호출을 비동기로 던지고 즉시 응답한다.** 커넥션 문제는 사라지지만 3rd party가 승인 여부를 즉시 알 수 없다. 결제 API는 동기 응답이 요구사항이므로 성립하지 않는다.
- **트랜잭션 안에서 호출하되 타임아웃을 짧게(예: 500ms) 잡는다.** 점유 시간을 줄일 뿐 구조는 그대로다. 게다가 결제 승인은 원래 수 초가 걸릴 수 있는 작업이라 짧은 타임아웃이 정상 거래를 실패시킨다.

## 검증 (2026-08-12 추가)

경계가 의도대로 그어졌는지 실행 중에 확인했다. 정적 분석만으로는 프록시 동작을 알 수 없어 트랜잭션 이름을 직접 찍었다.

```
PaymentService            = PaymentService            ← 프록시 없음
PaymentTransactionService = ...$$SpringCGLIB$$0       ← 프록시 있음
pay() 호출 전후 트랜잭션 활성 = false
```

`PaymentService`에는 `@Transactional`이 하나도 없어 스프링이 **프록시를 만들지 않았다.** 오케스트레이터가 트랜잭션을 열지 않는다는 것이 런타임에서 확인된다.

`settle()`·`confirm()` 안의 `private` 메서드(`settleApproved`, `confirmApproved`)가 같은 트랜잭션에서 도는지도 확인했다.

```
[public settle 진입] 활성=true 이름=...settle
[private 메서드 안]  활성=true 이름=...settle      ← 동일 트랜잭션
```

프록시는 빈 외부에서 `public` 메서드로 진입할 때만 트랜잭션을 열지만, 이 `private` 메서드들은 **이미 트랜잭션이 열린 뒤 호출**된다. 트랜잭션은 스레드에 바인딩되므로 그대로 이어진다. 위험한 경우는 반대로 `private`이나 자기호출 경로에 `@Transactional`을 붙여 두고 적용을 기대하는 것인데, 코드베이스에 그런 곳은 없다.

`settle()` 안의 쓰기가 하나가 아니라는 점이 중요하다.

```java
settleApproved() → walletStore.deductIfEnough()   // 쓰기 1, DB UPDATE
                   payment.complete(...)           // 메모리
ledgerStore.updateState(payment)                   // 쓰기 2, DB UPDATE
```

"쓰기가 마지막에 몰려 있으니 원자성이 없어도 된다"는 성립하지 않는다. 쓰기 1과 2 사이에서 실패하면 잔액은 빠졌는데 원장은 처리 중으로 남는다. `SettleAtomicityIT`가 그 지점에 예외를 주입해 차감이 롤백되는 것을 확인하며, `@Transactional`을 제거하면 실패한다.

`openPending`의 트랜잭션이 확정과 분리되어 있다는 것도 같은 테스트가 지킨다. 확정이 실패해도 처리 중 원장이 남아야 정합성 확인이 주워갈 수 있다 — 이쪽은 롤백되면 **안 되는** 방향이다.
