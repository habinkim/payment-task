# 0003. 잔액 차감은 조건부 UPDATE로 원자화한다

상태: Accepted

## 맥락

지갑 잔액을 차감하는 코드를 순진하게 쓰면 세 단계가 된다.

```
① 잔액을 조회한다
② 결제 금액보다 큰지 검사한다
③ 차감한 값을 저장한다
```

이 사이에 다른 요청이 끼어들 수 있다. 잔액 100인 지갑에 80짜리 결제 두 건이 동시에 들어오는 경우를 보자. 두 요청이 모두 ①에서 100을 읽고, 모두 ②를 통과하고, 모두 ③을 실행한다. 결과는 잔액 20이고 총 160이 결제됐다. 80이 어디선가 만들어진 것이다.

선불 지갑에서 이것은 회사가 손실을 떠안는다는 뜻이다. 고객이 보유하지 않은 외화가 결제됐고, 그 차액은 어딘가에서 메워야 한다. 잔액이 음수로 가는 것을 막는 것은 선택이 아니다.

과제 다이어그램의 Note도 이 지점을 짚고 있다. "지갑 잔액 확인, 금액 차감, 결제 이력 저장은 트랜잭션으로 처리하여 금액 정합성을 보장한다."

다만 트랜잭션으로 감싸는 것만으로는 부족하다. 기본 격리 수준(`REPEATABLE READ`)에서 위 시나리오는 그대로 재현된다. 읽기는 스냅샷을 보고, 쓰기는 마지막 값이 이긴다.

## 결정

조회와 검증과 차감을 **하나의 SQL로 합친다.**

```sql
UPDATE wallet
   SET balance = balance - :amount
 WHERE id = :walletId
   AND balance >= :amount
```

`WHERE`에 잔액 조건을 넣어 검증을 DB에 맡긴다. `balance = balance - :amount`는 애플리케이션이 읽은 값이 아니라 **DB가 현재 가진 값**을 기준으로 계산한다.

영향받은 행 수로 결과를 판정한다. 1이면 차감 성공, 0이면 잔액 부족이다. 0인 경우 `INSUFFICIENT_BALANCE`로 실패 처리한다.

대부분의 관계형 DB는 `UPDATE` 실행 시 대상 행에 배타 락을 건다. 두 요청이 동시에 들어오면 하나가 락을 잡고 처리한 뒤 커밋하고, 다른 하나는 그 결과를 보고 조건을 재평가한다. 뒤늦은 요청은 `WHERE balance >= 80`을 만족하지 못해 0행이 갱신된다.

과제 명세가 지정한 H2도 이 동작을 제공한다. 다만 락 경합의 세부 거동은 엔진마다 다르므로, 이 설계가 검증하는 것은 **어떤 순서로 처리되든 잔액이 음수가 되지 않는다**는 성질이지 특정 엔진의 락 구현이 아니다.

금액 컬럼은 `DECIMAL(19,4)`를 쓴다. `DOUBLE`은 이진 부동소수라 `0.1 + 0.2`가 정확히 `0.3`이 되지 않는다. 금액에서 이런 오차는 원장 불일치로 직결된다. 애플리케이션에서도 `BigDecimal`로만 다룬다.

## 결과

어떤 동시 요청이 들어와도 잔액은 음수가 되지 않는다. 이것을 동시성 테스트로 증명한다. 잔액 100인 지갑에 80짜리 결제 두 건을 동시에 넣어 하나만 성공하는지 확인한다.

락 보유 시간이 짧다. 조회부터 차감까지 하나의 문장이라 락 구간이 SQL 실행 시간으로 한정된다. 애플리케이션 왕복이 없으므로 락을 쥔 채 네트워크를 기다리는 구간이 존재하지 않는다.

대신 **차감 실패의 원인이 하나로 뭉뚱그려진다.** 0행 갱신은 잔액 부족일 수도 있고 지갑이 존재하지 않는 것일 수도 있다. 이를 구분하려면 별도 조회가 필요하다. 실패 경로에서만 한 번 더 조회하는 비용을 받아들인다. 정상 경로에는 영향이 없다.

또한 이 방식은 **차감 전후 잔액을 애플리케이션이 모른다.** 응답에 잔액을 담으려면 갱신 후 다시 조회해야 한다. 결제 응답에 잔액을 포함할지는 API 계약에서 결정하고, 포함한다면 실패 경로와 마찬가지로 추가 조회를 받아들인다.

## 검토한 대안

- **비관적 락(`SELECT ... FOR UPDATE`)으로 읽고 검증 후 차감한다.** 정합성은 동일하게 지켜진다. 다만 조회와 갱신 사이에 애플리케이션 왕복이 들어가므로 락 보유 시간이 길어진다. 검증 로직을 자바 코드로 쓸 수 있어 읽기는 낫지만, 이번 검증은 부등호 하나라 SQL로 표현하는 데 무리가 없다.
- **낙관적 락(`@Version`)으로 충돌을 감지하고 재시도한다.** 충돌이 드물 때 유리한 방식이다. 그러나 인기 지갑에 동시 결제가 몰리면 재시도가 반복되고, 재시도 횟수만큼 외부 결제 승인 이후 단계가 지연된다. 결제는 충돌 시 재시도보다 즉시 실패가 낫다.
- **애플리케이션 레벨 동기화(`synchronized`, `ReentrantLock`).** 단일 서버에서는 동작하지만 인스턴스를 늘리는 순간 무력해진다. 잔액 정합성을 프로세스 메모리에 의존하는 구조는 남겨두면 안 되는 부채다.
- **분산 락(Redis)으로 지갑 단위 직렬화.** 다중 인스턴스에서도 동작하지만 미들웨어가 하나 늘고, 락 획득 실패와 만료 처리가 새 실패 모드로 추가된다. 단일 서버에서 DB만으로 해결되는 문제라 도입하지 않는다. 서버 다중화가 확정되고 DB 락 경합이 실제로 측정될 때 다시 본다.
