# 0008. 도메인 객체와 JPA 엔티티를 분리한다

상태: Accepted

## 맥락

[PRD-001](../prd/PRD-001-결제플로우.md)에서 `Payment`와 `Wallet`을 순수 자바 객체로 만들었다. 생성자가 불변식을 강제하므로 유효하지 않은 상태의 결제는 존재할 수 없다. 결제번호 형식이 틀리거나 금액이 0이면 객체 자체가 만들어지지 않는다.

이제 이것을 저장해야 한다. 가장 단순한 방법은 도메인 객체에 `@Entity`를 붙이는 것이다. 클래스가 하나로 유지되고 변환 코드도 필요 없다.

그런데 JPA가 요구하는 것이 있다. 실제로 확인했다.

기본 생성자 없이 `@Entity`를 선언하고 Spring Boot 3.5.16, Hibernate 6.6에서 저장과 조회를 시도했다.

| 단계 | 결과 |
|---|---|
| 애플리케이션 기동 | 성공 |
| `persist()` | 성공 |
| **조회(`select`)** | **실패** — `org.hibernate.InstantiationException: No default constructor for entity` |

기동과 저장이 통과한 뒤 **조회 시점에** 터진다. Hibernate가 결과를 매핑할 때 리플렉션으로 빈 객체를 만든 다음 필드를 채우기 때문이다. 생성자를 우회한다.

이 실패 방식이 특히 나쁘다. 빌드가 통과하고 애플리케이션이 정상 기동하므로, 대리지표만 보면 문제가 없어 보인다.

따라서 도메인에 `@Entity`를 붙이려면 `protected Payment() {}`를 열어야 한다. 그 순간 다음이 가능해진다.

```java
Payment payment = new Payment();   // 결제번호도 금액도 없는 결제
```

같은 패키지나 하위 클래스에서 호출 가능하며, 리플렉션으로는 접근 제한과 무관하게 만들 수 있다. 불변식을 생성자에 둔 의미가 사라진다.

## 결정

**도메인 객체와 JPA 엔티티를 분리한다.**

```
payment/
├── domain/     Payment, PaymentStatus, FailureReason    프레임워크 의존 없음
└── infra/      PaymentEntity, PaymentRepository, PaymentLedgerStore
```

`PaymentEntity`는 JPA가 요구하는 것을 전부 받아들인다. 기본 생성자를 열고, 필드 접근을 허용하고, 세터를 두어도 무방하다. 이 클래스의 책임은 테이블 한 행을 표현하는 것뿐이며 비즈니스 규칙을 갖지 않는다.

변환은 `PaymentLedgerStore` 캡슐이 담당한다. 서비스는 캡슐을 통해 도메인 객체를 받고 도메인 객체를 넘긴다. `PaymentEntity`의 존재를 알지 못한다.

```
Service ──> PaymentLedgerStore ──> PaymentRepository ──> PaymentEntity
             (Payment 도메인 반환)
```

`Wallet`도 같은 구조를 따른다.

### 변환 위치

엔티티가 도메인을 알게 할 것인지, 그 반대로 할 것인지 정해야 한다. **엔티티가 도메인을 안다.** `PaymentEntity.toDomain()`과 `PaymentEntity.from(Payment)`를 둔다.

도메인이 엔티티를 알면 의존 방향이 뒤집혀 `payment.domain`이 `payment.infra`를 참조하게 된다. 아키텍처 테스트로 금지할 규칙이기도 하다.

### 도메인에는 Lombok을 쓰지 않는다

같은 이유로 도메인 객체에 Lombok 애노테이션을 붙이지 않는다. JPA의 기본 생성자와 성격이 같은 위협이기 때문이다.

`@Builder`는 필드를 하나씩 세팅해 객체를 만들므로 생성자 검증을 통째로 건너뛴다. `@NoArgsConstructor`는 기본 생성자를 그대로 열어준다. `@Setter`는 확정된 결제의 상태를 바깥에서 바꿀 수 있게 만들어 상태 전이 규칙을 무력화한다. 어느 쪽이든 이 ADR이 지키려는 것을 무너뜨린다.

도메인은 손으로 쓴 생성자와 접근자만 유지한다. 코드가 길어지지만, 어떤 경로로 객체가 만들어지는지 읽어서 확인할 수 있다는 이점이 그 비용을 넘는다.

반대로 인프라와 서비스 계층에서는 Lombok을 쓴다. 특히 `@RequiredArgsConstructor`는 `final` 필드만 골라 생성자를 만들므로 **필드 주입을 구조적으로 막는다.** 새 의존성을 추가하려면 `final`로 선언해야 하고, 그러면 생성자에 자동으로 포함된다. `@Autowired` 필드 주입은 쓰지 않는다.

두 규칙 모두 아키텍처 테스트로 강제한다.

## 결과

도메인 불변식이 실제로 지켜진다. `new Payment(...)`는 여전히 유효한 결제만 만들고, 기본 생성자는 어디에도 없다. 이 사이클에서 작성한 단위 테스트 36건이 계속 의미를 갖는다.

도메인 객체를 인프라 없이 테스트할 수 있다. Spring 컨텍스트도, H2도 필요 없다. 단위 테스트가 밀리초 단위로 끝난다.

**대신 클래스가 늘고 변환 코드가 생긴다.** 결제 하나를 다루는 데 `Payment`와 `PaymentEntity` 두 클래스를 유지해야 하고, 필드를 추가하면 두 곳을 고쳐야 한다. 필드를 한쪽에만 추가하는 실수가 가능하다.

이 비용을 받아들이는 근거는 대상이 **결제 원장**이라는 점이다. 상태 전이 규칙이 실재하고, 잘못된 상태가 만들어지면 금액 정합성이 깨진다. 단순 조회용 테이블이었다면 분리하지 않았을 것이다.

**변환 시점의 상태 복원 문제가 있다.** DB에서 읽은 결제가 `COMPLETED`라면, `toDomain()`은 생성자로 `PENDING` 객체를 만든 뒤 `complete()`를 호출하는 방식으로는 복원할 수 없다. 종료 상태 검사에 걸리거나 부수 필드가 어긋난다. 저장된 상태를 그대로 주입하는 복원 전용 경로를 도메인에 두어야 한다. 이 경로는 검증을 우회하므로 패키지 프라이빗이나 정적 팩터리로 제한해 일반 생성과 구분한다.

## 검토한 대안

- **도메인에 `@Entity`를 붙이고 `protected` 기본 생성자를 연다.** 클래스가 하나뿐이고 변환 코드가 없다. 널리 쓰이는 방식이기도 하다. 그러나 불변식을 우회하는 생성 경로가 열리고, 이번 사이클에서 생성자 검증에 들인 노력이 무의미해진다. 결제 원장에서 "금액 없는 결제 객체"가 만들어질 수 있는 상태를 남기고 싶지 않다.

- **도메인에 `@Entity`를 붙이되 기본 생성자를 `private`으로 두고 Lombok `@NoArgsConstructor(access = PRIVATE)`를 쓴다.** 접근을 좁힐 수는 있으나 Hibernate는 리플렉션으로 접근하므로 실효가 없다. 가려질 뿐 경로는 그대로 열려 있다.

- **JPA를 쓰지 않고 JdbcTemplate으로 직접 매핑한다.** 기본 생성자 문제가 사라지고 도메인을 그대로 쓸 수 있다. 그러나 매핑과 쿼리를 전부 직접 작성해야 하고, 이 과제 규모에서 얻는 것보다 잃는 것이 많다. 조건부 UPDATE([0003](0003-atomic-balance-deduction.md))처럼 직접 SQL이 필요한 곳은 JPA 안에서도 네이티브 쿼리로 해결된다.

- **레코드(record)로 도메인을 만들고 엔티티와 분리하지 않는다.** 레코드는 불변이라 상태 전이를 표현할 수 없다. `complete()`가 새 인스턴스를 반환하는 방식으로 우회할 수 있으나, 결제 원장은 식별자가 고정된 채 상태만 바뀌는 대상이므로 의미가 어긋난다.
