# 0007. 모의 게이트웨이를 운영 코드에 두고 프로파일로 전환한다

상태: Accepted

## 맥락

과제의 외부 결제 API는 "가상의 3rd party"다. 실존하지 않으므로 우리가 만들어야 한다.

여기서 모의 구현을 어디에 둘 것인지가 갈린다. 흔한 반사적 판단은 테스트 소스에 두는 것이다. 모의 구현은 테스트 도구라는 통념 때문이다.

그러나 이 과제에서는 성립하지 않는다. **테스트 소스는 실행 산출물에 포함되지 않는다.** `bootJar`로 만든 jar에도, `bootRun`으로 띄운 애플리케이션에도 `src/test`의 클래스는 클래스패스에 없다. 모의 구현을 테스트 소스에 두면 프로파일로 활성화하는 것 자체가 불가능하다.

그러면 앱을 실행했을 때 결제를 처리할 상대가 없어진다. 평가자가 저장소를 클론해 앱을 띄우고 결제를 호출하면 연결 실패가 난다. 자족 실행이 깨진다.

이 문제를 우회하려고 앱 안에 스텁 HTTP 엔드포인트를 두는 방법을 검토했었다. 그러면 HTTP 클라이언트가 같은 애플리케이션의 컨트롤러를 호출하게 된다. 요청이 자기 자신에게 나갔다가 돌아오는 구조다. 톰캣 스레드를 하나 더 쓰고, 호출 경로를 설명하기도 어렵다.

한 걸음 물러서면 전제가 잘못됐음이 드러난다. **이 과제에서 모의 게이트웨이는 테스트 편의가 아니라 요구사항이다.** 명세가 가상의 3rd party를 전제했으므로, 모의 구현이 곧 이 시스템의 정상 동작 경로다. 정상 동작을 담당하는 코드가 테스트 소스에 있을 이유가 없다.

## 결정

**모의 게이트웨이를 운영 코드(`src/main`)에 두고, 프로파일로 실제 연동 구현과 전환한다.**

```
src/main/.../gateway/
├── PaymentGatewayClient          인터페이스
├── MockPaymentGatewayClient      @Profile("!real") 기본 활성
└── HttpPaymentGatewayClient      @Profile("real")  실제 연동
```

`MockPaymentGatewayClient`가 기본이다. 별도 설정 없이 앱을 띄우면 이 구현이 동작한다. 평가자는 저장소를 클론해 `./gradlew bootRun` 한 줄로 결제 전 경로를 눌러볼 수 있다.

`HttpPaymentGatewayClient`는 실제 게이트웨이가 생겼을 때를 위한 구현이다. `real` 프로파일에서만 활성화된다. 두 구현은 배타적이라 한쪽이 뜨면 다른 쪽은 생성되지 않는다.

앱 내부 스텁 컨트롤러는 두지 않는다. 모의 구현이 프로세스 안에서 응답하므로 자기 자신을 HTTP로 호출할 이유가 사라졌다.

### 검증 책임의 분담

모의 구현과 WireMock은 검증하는 대상이 다르다. 둘 다 필요한 이유다.

| 대상 | 검증 주체 | 무엇을 확인하나 |
|---|---|---|
| 서비스 로직, 상태 전이, 실패 분류 | `MockPaymentGatewayClient` | 승인 결과별로 원장이 올바른 상태로 가는가 |
| 타임아웃 설정, 연결 실패, 상태 코드 처리 | WireMock + `HttpPaymentGatewayClient` | HTTP 계층 설정이 실제로 동작하는가 |

모의 구현은 **결과를 만든다.** 타임아웃 시나리오라면 `GatewayApproval.inDoubt()`를 반환한다. 실제로 기다리지 않는다. 그래야 단위 테스트가 밀리초 단위로 끝난다.

WireMock은 **설정을 검증한다.** `withFixedDelay()`로 응답을 늦춰 read timeout이 실제로 걸리는지 본다. `withFault(CONNECTION_RESET_BY_PEER)`로 연결을 끊는다. 이런 조작은 인터페이스 구현체로 재현할 수 없다.

이 분담이 없으면 타임아웃 처리([0004](0004-timeout-is-indoubt.md))가 문서로만 남는다. 모의 구현이 `inDoubt()`를 반환하는 것은 "타임아웃이 났다고 내가 선언한 것"이지, read timeout을 30초로 잘못 설정했는지는 알려주지 않는다.

### 시나리오 트리거 규약

모의 구현은 `paymentNo` 접두어로 시나리오를 판정한다.

```
TIMEOUT-20260810-001    결과 미상
ERR500-20260810-001     외부 서버 오류
ERR400-20260810-001     잘못된 요청
DECLINE-20260810-001    승인 거절
SLOW-20260810-001       지연 응답
(접두어 없음)            정상 승인
```

`paymentNo`는 3rd party가 자유롭게 만드는 값이므로([0002](0002-payment-no-as-idempotency-key.md)) 요청 스펙을 바꾸지 않고 시나리오를 지정할 수 있다. 값이 원장에 남아 어떤 조건에서 만들어진 건인지 추적된다. 실제 결제 게이트웨이들이 테스트 환경에서 쓰는 방식이기도 하다.

**접두어 해석은 모의 구현 안에만 둔다.** `HttpPaymentGatewayClient`는 접두어의 존재를 알지 못하며, 받은 `paymentNo`를 그대로 외부에 전달한다. 시뮬레이션 규약이 실제 연동 경로로 새어 들어가지 않게 하는 경계다.

## 결과

외부 의존 없이 앱이 자족 동작한다. 평가자가 클론해서 바로 전 경로를 확인할 수 있다.

자기 자신을 HTTP로 호출하는 구조가 사라졌다. 호출 경로가 한 단계 짧아지고 설명하기 쉬워졌다.

인터페이스에 실제 구현이 둘 생겼다. 추상화는 두 번째 구현이 생길 때 정당화된다는 기준([0006](0006-single-server-no-middleware.md))을 이제 충족한다.

대신 **운영 코드에 모의 구현이 포함된다.** 실서비스라면 배포 산출물에 모의 구현이 섞이는 것을 경계해야 한다. 두 가지로 방어한다. 첫째, 프로파일로 배타 활성화하여 `real`에서는 모의 빈이 생성되지 않는다. 둘째, 이 시스템에서 실제 게이트웨이는 아직 존재하지 않으므로 모의 구현이 유일한 정상 경로다. 실제 연동이 생기는 시점에 모의 구현을 별도 모듈로 분리하거나 제거한다.

그리고 **기본 프로파일에서는 HTTP 계층 설정이 한 번도 실행되지 않는다.** connect와 read 타임아웃, 커넥션 풀 설정은 `real` 프로파일에서만 경로에 놓인다. 이 설정의 정합성은 앱을 띄워보는 것으로 확인되지 않고 통합 테스트로만 담보된다. 설정을 바꿔놓고 앱이 잘 뜬다고 안심하면 안 되는 구조다.

**`HttpPaymentGatewayClient`는 기본 프로파일에서 호출되지 않는다.** 죽은 코드로 보일 수 있으나 통합 테스트가 `real` 프로파일로 이것을 실행 대상으로 삼는다. WireMock을 상대로 타임아웃과 연결 실패를 검증하는 경로가 곧 이 클래스다.

## 검토한 대안

- **모의 구현을 테스트 소스에 둔다.** 목은 테스트 도구라는 통념에는 맞지만, 테스트 소스는 실행 산출물에 포함되지 않아 앱이 자족 동작하지 못한다. 이 과제에서 모의 게이트웨이는 테스트 편의가 아니라 요구사항이므로 전제가 어긋난다.
- **앱 안에 스텁 HTTP 엔드포인트를 두고 클라이언트가 호출한다.** 자족 실행은 되지만 애플리케이션이 자기 자신에게 HTTP 요청을 보내는 구조가 된다. 톰캣 스레드를 추가로 쓰고 호출 경로가 한 단계 길어져 설명이 어려워진다. 게다가 이 방식으로도 타임아웃 설정 검증은 되지 않아 WireMock은 여전히 필요하다.
- **모의 구현만 두고 실제 연동 구현을 만들지 않는다.** 지금 호출할 외부가 없으니 간단하다. 그러나 인터페이스에 구현이 하나뿐이면 추상화의 근거가 약하고, HTTP 계층 설정을 검증할 대상이 사라진다.
- **WireMock을 실행 시에도 띄워 모의 게이트웨이로 쓴다.** 테스트와 실행에서 같은 도구를 쓸 수 있지만, 평가자가 앱과 별도로 WireMock을 기동해야 해 자족 실행을 해친다.
- **실제 게이트웨이의 샌드박스를 연동한다.** 가장 현실적인 검증이 되지만 과제가 요구한 것은 가상의 3rd party이고, 외부 서비스에 의존하면 네트워크 없이는 실행도 테스트도 되지 않는다.
