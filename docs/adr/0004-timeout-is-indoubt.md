# 0004. 타임아웃은 실패가 아니라 결과 미상으로 다룬다

상태: Accepted

## 맥락

과제 명세는 실패 사유를 두 가지로 제시한다. 잔액이 부족하면 `INSUFFICIENT_BALANCE`, 외부 오류나 내부 장애면 `SYSTEM_ERROR`다. 외부 호출이 실패하는 모든 경우를 `SYSTEM_ERROR`로 묶으면 요구사항은 충족된다.

그런데 외부 호출의 실패는 한 종류가 아니다.

외부가 500을 반환했다면 처리되지 않았다는 것이 확실하다. 연결이 거부됐다면 요청이 도달조차 못 했다. 400이면 우리가 잘못 보낸 것이고 다시 보내도 같은 결과다.

**타임아웃은 다르다.** 응답이 오지 않았다는 사실만 알 뿐, 외부에서 무슨 일이 일어났는지 모른다. 요청이 도달하지 못했을 수도 있고, 도달해서 승인까지 났는데 응답만 유실됐을 수도 있다. 후자라면 고객 계좌에서는 이미 돈이 나갔다.

이 상태를 `FAILED`로 확정하면 어떻게 되는가. 시스템은 실패로 기록했는데 외부에서는 결제가 성립한 상태가 된다. 고객은 돈이 빠져나갔는데 서비스에서는 결제 실패라고 안내받는다. 외환 서비스에서 이것은 곧바로 CS 문의이고, 대사 없이는 해결되지 않는다.

과제 개요의 첫 문장이 이 지점을 가리키고 있다. 이 시스템은 "고객의 결제 이력, **정합성을 확인**하기 위한 서버 시스템"이다. 단순히 이력을 쌓는 것이 아니라 정합성을 확인하는 것이 요구사항이다. 확인할 대상이 없다면 그 문구는 의미가 없다.

## 결정

**타임아웃과 결과를 알 수 없는 통신 실패는 `UNKNOWN` 상태로 남긴다.** 명세에 없는 상태를 추가한다.

```
PENDING ─┬─→ COMPLETED
         ├─→ FAILED
         └─→ UNKNOWN ─┬─→ COMPLETED
                      └─→ FAILED
```

`UNKNOWN`은 종료 상태가 아니다. 조회를 통해 `COMPLETED`나 `FAILED`로 확정된다. 확정되기 전까지 잔액은 차감하지 않는다. 확정되지 않은 것을 근거로 돈을 움직이지 않는다.

확정 수단은 두 가지를 둔다.

- **관리자용 정합성 확인 API** — `UNKNOWN` 건을 외부에 재조회해 상태를 확정한다. 운영자가 특정 건을 지목해 실행할 수 있다.
- **주기 스케줄러** — 일정 간격으로 `UNKNOWN` 건을 모아 자동 확정을 시도한다.

동시에 실패를 **재시도 가능 여부**로 분류해 원장에 기록한다.

| 상황 | 사유 | 상태 | 재시도 |
|---|---|---|---|
| 승인 거절 | `PAYMENT_DECLINED` | FAILED | 불가 |
| 잔액 부족 | `INSUFFICIENT_BALANCE` | FAILED | 불가 |
| 4xx 응답 | `SYSTEM_ERROR` | FAILED | 불가 |
| 5xx 응답 | `SYSTEM_ERROR` | FAILED | 가능 |
| 연결 실패 | `SYSTEM_ERROR` | FAILED | 가능 |
| **타임아웃** | `SYSTEM_ERROR` | **UNKNOWN** | 가능 |

명세가 요구한 `SYSTEM_ERROR` 사유는 그대로 유지한다. 재시도 가능 여부는 별도 필드로 병기하는 것이지 사유를 대체하지 않는다.

원장에는 외부 거래 식별자, 외부 응답 코드, 요청 시각과 응답 시각을 함께 남긴다. CS가 PG사에 대조 문의를 하려면 이 값들이 있어야 한다. 명세에 없는 필드지만, "고객 문의 대응에 활용"이라는 요구가 이것 없이는 성립하지 않는다.

## 결과

미아 거래가 조용히 만들어지지 않는다. 결과를 모르는 건은 모른다고 기록되고, 확정 절차가 붙는다.

CS가 실패 이력만 보고 판단할 수 있게 된다. "재시도하면 되나요"라는 질문에 원장의 재시도 가능 필드로 답한다. "PG사에 확인해 주세요"라는 요청에는 외부 거래 식별자를 넘긴다.

대신 **상태가 하나 늘어 처리 분기가 늘었다.** 조회 API는 `UNKNOWN`을 어떻게 표현할지 정해야 하고, 클라이언트도 이 상태를 이해해야 한다. 응답에서는 처리 중임을 나타내되 실패로 오인되지 않게 코드를 분리한다.

또한 **명세에 없는 상태를 추가한 것이 요구사항 이탈로 읽힐 위험이 있다.** 이 판단의 근거는 개요의 "정합성을 확인하기 위한" 문구이며, `SYSTEM_ERROR` 사유 자체는 명세대로 저장하므로 요구사항은 그대로 충족된다. README에 이 관계를 명시한다.

`UNKNOWN` 건이 계속 쌓이면 수동 처리 한계를 넘는다. 그 시점에 자동 대사 배치를 검토한다. 지금은 건수가 적어 스케줄러 하나로 충분하다.

## 검토한 대안

- **타임아웃을 그대로 `FAILED`로 확정한다.** 명세를 가장 곧이곧대로 따르는 선택이고 구현이 단순하다. 그러나 외부에서 승인된 건을 실패로 기록하는 경우가 생긴다. 결제 도메인에서 받아들이기 어려운 오류다.
- **타임아웃을 `PENDING`으로 남긴다.** 상태를 늘리지 않아도 되고, `PENDING`의 의미를 "처리 중이거나 결과 미상"으로 넓히면 된다. 다만 방금 요청이 들어와 처리 중인 건과, 외부 호출이 타임아웃돼 확정이 필요한 건이 구분되지 않는다. 운영에서 "지금 처리 중인 것"과 "손봐야 하는 것"을 가려내지 못하면 모니터링이 무의미해진다.
- **타임아웃 시 즉시 외부에 재조회해 그 자리에서 확정한다.** 사용자 응답 시간 안에 해결하려는 시도지만, 외부가 느려서 타임아웃이 난 상황에서 같은 외부에 다시 묻는 것은 성공 가능성이 낮다. 응답만 더 늦어진다. 확정은 응답 이후로 미루는 것이 맞다.
- **타임아웃 시 취소 API를 호출해 보상한다.** 확실하게 되돌리는 방법처럼 보이지만, 승인되지 않은 건에 취소를 거는 경우가 생기고 취소 자체도 타임아웃될 수 있다. 무엇이 일어났는지 모르는 상태에서 보상부터 시도하면 상태가 더 꼬인다. 먼저 조회해 사실을 확인하고, 그 다음에 보상 여부를 결정한다.
