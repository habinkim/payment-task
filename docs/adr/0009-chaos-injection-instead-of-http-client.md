# 0009. 실제 HTTP 연동 대신 확률 기반 장애 주입을 둔다

상태: Accepted

[0007](0007-mock-gateway-in-production.md)의 "검증 책임의 분담" 절을 대체한다. 나머지 결정(모의 구현을 운영 코드에 두고 설정으로 전환)은 그대로 유효하다.

## 맥락

[0007](0007-mock-gateway-in-production.md)은 검증을 둘로 나눴다. 모의 구현이 *결과를 만들고*, WireMock을 상대하는 `HttpExternalPaymentClient`가 *HTTP 계층 설정을 검증한다*는 구도였다. `read-timeout: 3s`가 실제로 걸리는지는 인터페이스 구현체로 알 수 없다는 것이 근거였다.

그 근거는 지금도 맞다. 그러나 전제가 틀렸다.

**연동할 실제 게이트웨이가 없다.** 과제가 요구한 것은 가상의 3rd party이고, 이 시스템은 앞으로도 실제 결제사에 붙지 않는다. `HttpExternalPaymentClient`를 만들어도 향할 곳은 테스트의 WireMock뿐이다.

그러면 `read-timeout: 3s`는 **존재하지 않는 외부를 향한 설정**이 된다. 그 설정이 옳은지 검증하려고 WireMock을 띄우는 것은 검증을 위한 검증이다. 설정을 지우면 검증할 대상도 함께 사라진다.

한편 실제로 부족한 것이 따로 있다. 모의 구현은 `merchantPaymentNo` 접두어로만 실패한다. 평가자가 `TIMEOUT-`을 붙여야 타임아웃을 보고, 붙이지 않으면 영원히 성공한다. 그런데 **정상 결제를 반복하다 우연히 실패를 만나는 상황**이야말로 재시도와 정합성 확인이 존재하는 이유다. 접두어 방식으로는 그 상황이 재현되지 않는다.

## 결정

`HttpExternalPaymentClient`와 WireMock 검증을 만들지 않는다. 대신 모의 구현에 **확률 기반 장애 주입**을 둔다.

```yaml
payment:
  gateway:
    mode: mock
    chaos:
      enabled: false
      timeout-rate: 0.0
      failure-rate: 0.0
```

기본값은 전부 꺼짐이다. 켜지 않으면 기존 동작이 그대로 유지되므로, 이 기능이 다른 테스트를 흔들지 않는다.

**접두어 지정이 확률보다 우선한다.** `TIMEOUT-`을 붙인 요청은 장애 주입이 켜져 있든 아니든 항상 타임아웃이 된다. 의도한 시나리오가 확률에 휘둘리면 나머지 통합 테스트가 전부 불안정해진다.

```
접두어 있음  →  접두어대로 (확정적)
접두어 없음  →  카오스 꺼짐이면 승인
             →  카오스 켜짐이면 확률에 따라 타임아웃 · 실패 · 승인
```

**난수를 생성자로 주입한다.** 테스트는 시드를 고정해 결정론적으로 검증한다. 확률 로직의 검증을 확률에 맡기면 간헐적으로 깨지는 테스트가 된다. `Clock`을 주입한 것과 같은 이유다.

**쓰이지 않는 설정을 제거한다.** `payment.gateway.base-url`, `connect-timeout`, `read-timeout`은 향할 대상이 없으므로 지운다. 코드가 읽지 않는 설정이 파일에 남아 있으면 "어딘가에서 쓰이겠거니" 하는 오해를 만든다.

## 결과

**스케줄러가 실제로 하는 일을 볼 수 있다.** 장애 주입을 켜고 결제를 반복하면 `UNKNOWN`이 자연스럽게 쌓이고, 정합성 확인 스케줄러가 그것을 집어 확정한다. 접두어로 한 건씩 만들어 넣는 것과는 다른 그림이다.

**부하 상황의 동작을 눌러볼 수 있다.** 실패율을 올리면 재시도 분류와 미아 거래 카운터가 어떻게 움직이는지 관측된다. 운영 대응을 설계할 때 쓰는 수단이며, 이 과제에서 실패 이력이 "운영 모니터링과 고객 문의 대응"을 위한 것이라는 요구와 맞닿는다.

대신 **HTTP 계층 설정이 여전히 검증되지 않는다.** 다만 이제는 검증할 설정 자체가 없다. 실제 게이트웨이를 붙이는 시점에 `HttpExternalPaymentClient`와 타임아웃 설정을 함께 만들고, 그때 WireMock 검증을 추가한다. 지금 만들어 두는 것은 쓰이지 않는 코드를 미리 쌓는 일이다.

**장애 주입 코드가 운영 코드에 포함된다.** 모의 구현이 이미 운영 코드에 있으므로([0007](0007-mock-gateway-in-production.md)) 새로운 성격의 문제는 아니다. 기본값이 꺼짐이라 명시적으로 켜지 않으면 동작하지 않는다.

## 검토한 대안

- **원래 계획대로 `HttpExternalPaymentClient`와 WireMock을 만든다.** 타임아웃 설정을 실제로 검증할 수 있고, 실제 연동으로 가는 길이 열려 있다는 것도 보여준다. 그러나 검증 대상인 설정이 어디에도 쓰이지 않으며, 향할 외부가 없는 클라이언트는 테스트에서만 실행되는 코드다. 과거 유사 과제에서 규모가 요구하지 않는 구성을 미리 만들어 감점 요인으로 자평한 적이 있다.

- **둘 다 만든다.** 장애 주입과 HTTP 클라이언트를 모두 두면 검증 범위가 넓어진다. 그러나 쓰이지 않는 쪽의 유지 비용이 계속 발생하고, 리뷰에서 "이건 왜 있나"를 두 번 설명해야 한다.

- **접두어 방식만 유지한다.** 아무것도 더하지 않아 가장 단순하다. 그러나 우연히 발생하는 실패를 재현할 수 없어, 스케줄러와 정합성 확인이 실제로 필요한 상황을 만들지 못한다. 기능은 있는데 그 기능이 필요한 상황을 보여줄 수 없는 상태가 된다.

- **난수를 주입하지 않고 `Math.random()`을 직접 쓴다.** 코드가 짧아지지만 확률 로직을 검증할 수 없다. 테스트가 간헐적으로 깨지거나, 깨지지 않게 하려고 검증을 포기하게 된다.
